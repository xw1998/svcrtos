# 配置区与安装策略

> 本文回答两个问题：**这台设备上，镜像是怎么落位的**，以及**怎么在"不改固件"的前提下改这件事**。
> 操作步骤见《SVCrtOS应用安装与调试指南.md》。

---

## 0. 一句话概括

镜像的落位方式**不在固件里写死**：设备上单独有一个 128 KB 的 **CONFIG 扇区**，里面放一条
512 字节的**配置记录**。上电时内核先读它，读到了就按它办，读不到（或校验不过）就回退到
`config/svcrt_partition.h` 里的**编译期默认值**。

于是同一份固件可以有两副面孔：

| 场景 | 配置 | 效果 |
|---|---|---|
| 交付给客户二次开发 | `mode = fixed` | 每个槽位地址固定，客户可以直接用 Keil/烧录器往**固定地址**灌 App 和驱动，挂调试器下断点 |
| 现场升级 / 无烧录器 | `mode = auto` | 内核在池内细粒度首适配分配，镜像可搬移，卸载时按策略压实回收 |

**两种模式整机二选一**，不混用。混着用会让"这个地址到底属于谁"失去唯一答案。

## 1. Flash 分区（F427，1 MB）

```
0x08000000 ┌──────────────────────────────┐
           │ KERNEL        256 KB         │  内核（含安装任务、shell、lwIP）
0x08040000 ├──────────────────────────────┤
           │ CONFIG        128 KB         │  设备端配置记录（只用开头 512 B）
0x08060000 ├──────────────────────────────┤
           │ IMAGE_POOL    640 KB         │  统一镜像池：App 与驱动共用
           │  5 × 128 KB 扇区             │
0x080FFFFF └──────────────────────────────┘
```

`IMAGE_POOL_SIZE` 是 `CHIP_FLASH_SIZE - KERNEL_SIZE - CONFIG_SIZE` 的余数，
所以**改芯片容量只要改 `CHIP_FLASH_SIZE`**，其余地址与所有 `.sct` 自动重算。

CONFIG 占的是**一整个物理扇区**（F4 上是 128 KB），因为它必须能被单独擦除——
Flash 只支持"整片擦回 1"，写在里面的记录要能被重写就得独占一片。
代价是池少一个扇区：F427 的池从 896 KB 降到 768 KB。

KERNEL 现在是 **256 KB**（lwIP 编进内核，见 [lwIP协议栈接入](lwIP协议栈接入.md)），
所以池再少 128 KB，实际是 640 KB（5 个扇区，扣掉压实余量后可分配 512 KB）。
KERNEL 大小必须是 2 的幂（MPU 区域约束），撤掉 `SVCRT_USE_LWIP` 就可以用 `-D` 覆盖回 128K。

F401（512 KB）的分区形状相同，池是 256 KB / 2 个扇区。

### 1.1 池的分配粒度

| 参数 | 值 | 说明 |
|---|---|---|
| `IMAGE_POOL_SECTOR` | 128 KB | 物理扇区，**擦除**的最小单位 |
| `SVCRT_POOL_ALLOC_UNIT` | 1 KB | 分配粒度，**落点对齐**的最小单位 |
| `POOL_RESERVE_SECTORS` | 1 | 压实时的腾挪余量，保留一个扇区不参与分配 |
| `SLOT_MAX` | 16 | 分区表能同时登记的镜像数（App + 驱动共用） |

"擦除按扇区、落点按 1 KB"是这套设计的关键：一个 10 KB 的 App 在 auto 模式下只占
11 KB 左右，不再整扇区占用。

## 2. RAM 布局（F427，128 KB）

```
0x20000000 ┌─────────────────┐
           │ SHARE_RAM   8 KB│  分区表（内核与 App 的数据交换面）
0x20002000 ├─────────────────┤
           │ KERNEL_RAM 56 KB│  内核数据 / 内核任务栈
0x20010000 ├─────────────────┤
           │ SLOT_RAM   64 KB│  镜像 RAM 池（伙伴分配）
0x2001FFFF └─────────────────┘
```

镜像的 `.data/.bss/栈` 全部从 `SLOT_RAM` 里切，块大小必须是 2 的幂且在
`[SLOT_RAM_MIN_BLOCK, SLOT_RAM_MAX_BLOCK]` = `[1 KB, 32 KB]` 之间——
这不是审美要求，是 **MPU region 的硬约束**（region 必须 2 的幂且按大小对齐）。

`KERNEL_RAM_SIZE = CHIP_RAM_SIZE - SHARE_RAM_SIZE - SLOT_RAM_TOTAL`，**不是 2 的幂**，
因此内核任务的 MPU RAM 窗口会退化成一整块芯片 RAM。内核任务是可信代码，
不影响隔离语义。

### 2.1 开发槽位的 RAM 窗口

裸镜像（见 §5）没有镜像头，扫描器读不到它的 `ram_size`，所以内核按一张**静态表**
给每个开发槽位划一个固定窗口：

```
窗口基址 = SLOT_RAM_BASE + (起始单元号 % SVCRT_DEV_SLOT_MAX) × SVCRT_DEV_RAM_WINDOW
```

这条公式有**两个实现**，必须永远一致：

- 内核：`config/svcrt_partition.h` 的 `SVCRT_DEV_SLOT_RAM_BASE(unit)`，
  由 `svcrt_loader.c` 在认领裸镜像时 `svcrt_ptable_ram_bind()` 绑给槽位；
- 工具链：`tools/gen_scatter.py` 的 `dev_ram_base(unit)`，生成 App 的 `.sct`。

两边算出来的地址必须相等，否则 App 链接时以为栈在 A、内核启动时把栈放在 B，
表现是"能下载、能启动、跑一会儿就崩"。

F427：`SVCRT_DEV_RAM_WINDOW = 16 KB`，4 个开发槽位 → 64 KB，**正好占满 SLOT_RAM**。
这意味着**开着 4 个开发槽时，auto 模式没有 RAM 可分**。两个策略本身互斥（§3），
所以正常不会同时发生；但如果你在 fixed 设备上又想装一个 auto 镜像，它会因为拿不到
RAM 块而启动失败（`SVCRT_LOADER_ERR_STATE`）。

F401：`SVCRT_DEV_RAM_WINDOW = 8 KB`，4 × 8 KB = 32 KB = `SLOT_RAM_TOTAL`。

## 3. 两种安装策略

`mode` 字段（配置记录偏移 12，也是 `svcrt_layout_mode()` 的返回值）：

| 值 | 名称 | 落位 | 卸载 |
|---|---|---|---|
| `0` | `SVCRT_LAYOUT_MODE_AUTO` | 池内 1 KB 粒度首适配；落点由内核决定 | 擦除本镜像区间；按 `reclaim_mode` 决定是否搬移邻居压实 |
| `1` | `SVCRT_LAYOUT_MODE_FIXED` | 按槽位表把整段扇区划给槽；落点 = 配置里写的地址 | 只擦本槽，不搬移、不压实，空间不退回池 |

### 3.1 auto 模式的回收力度

`reclaim_mode` 决定卸载后怎么收：

| 值 | 行为 |
|---|---|
| `0` | 不压实：只擦除空出来的扇区（前提是整片扇区都没人用） |
| `1` | 压实：把后面的镜像往前搬，腾出连续空间 |

注意 Flash 的物理限制：**只有整片物理扇区（F4 上 128 KB）都空出来才会真的擦**。
池底的镜像不可下移，所以"某个扇区里还留着别人"时，那块空间会一直钉在池里。

### 3.2 fixed 模式的语义

- Flash 落点按槽固定；
- RAM 窗口按槽固定（§2.1）；
- 卸载只擦本槽，**不做压实、空间不退回池**——这个地址永远属于这个槽；
- 已登记的槽位表由配置记录给出（`svcrt_cfg_slot_t slot[8]`）。

固定模式下"覆盖安装"是允许的：往同一个槽再灌一次镜像即可。
但**正在运行的镜像不能被覆盖**（内核返回 `SVCRT_LOADER_ERR_BUSY`），
因为擦写会让它当场跑飞。

## 4. 配置记录的二进制格式

写在一整个 CONFIG 扇区的**开头 512 字节**，小端、无填充。
定义在 `kernelsrc/include/svcrt_layout_def.h`（**UTF-8 + LF**，
上位机工具 `tools/svcrt_layout.py` 是同一份结构的 Python 版本）。

### 4.1 记录头

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0 | `magic` | `0x47464353`，即 ASCII `"SCFG"` |
| 4 | `version` | 当前为 `1` |
| 8 | `hw_compat_id` | 芯片兼容标识：F427 = `0x42700005`，F401 = `0x40100005` |
| 12 | `mode` | 0 = auto，1 = fixed |
| 16 | `seq` | 写入序号，单调递增；用于判断"哪次写的更新" |
| 20 | `slot_count` | 有效槽位数（仅 fixed 模式有意义，上限 8） |
| 24 | `flags` | 见 §4.3 |
| 28 | `reclaim_mode` | 见 §3.1 |

`hw_compat_id` 是**防串台**用的：把 F427 的配置记录写到 F401 上，内核会以
`SVCRT_CFG_ERR_HW` 拒收，而不是拿着错误的地址去擦别人的 Flash。

### 4.2 槽位表（fixed 模式）

`svcrt_cfg_slot_t slot[8]`，每条 32 字节：

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0 | `base` | Flash 落点（固定地址） |
| 4 | `size` | 区段长度 |
| 8 | `type` | 1 = App，2 = 驱动 |
| 12 | `ram_base` | RAM 窗口基址 |
| 16 | `ram_size` | RAM 窗口长度 |
| 20 | `autostart` | 上电是否自动启动 |
| 24 | `flags` | 保留，必须为 0 |
| 28 | `reserved` | 保留，必须为 0 |

### 4.3 `flags` 位

| 位 | 名称 | 说明 |
|---|---|---|
| `0x1` | `SVCRT_CFG_FLAG_RAW_ALLOW` | 允许池内直接烧录的裸镜像（开发调试用） |

**未知位一律拒收**（`SVCRT_CFG_ERR_RESERVED`）。把看不懂的位当成 0 用，
等于替设备猜配置——配置区里写了但设备没照做，是最难查的一类问题。

### 4.4 运行期参数

| 偏移 | 字段 | 当前状态 |
|---|---|---|
| 288 | `log_level` | **生效**：内核日志级别 |
| 292 | `fault_restart_max` | **生效**：连续故障重启上限 |
| 296 | `boot_delay_ms` | **生效**：自启前先忙等这么久（上限 `SVCRT_CFG_BOOT_DELAY_MAX` = 60000） |
| 300 | `watchdog_ms` | **拒收**（见下） |
| 304 | `heap_size` | **拒收** |
| 308 | `thread_stack_default` | **拒收** |
| 312 | `tool_version` | 写入记录的上位机工具版本，仅作溯源 |
| 316 | `reserved[48]` | 保留，必须为 0 |
| 508 | `crc32` | 覆盖 0..507 的 CRC32（**计算时 crc 字段本身按 0 参与**） |

三个"拒收"项的理由写在这里，免得以后有人以为是漏了：

- **`watchdog_ms`**：内核没有 IWDG 端口层。而且一次 128 KB 扇区擦除要 ~2 秒，
  擦除期间喂不了狗，配一个内核兑现不了的看门狗超时值比不配更危险。
- **`heap_size`**：POSIX 堆是 **App 侧**的静态 arena，内核不持有堆。
  App 想要多大堆，应该在 App 工程里声明。
- **`thread_stack_default`**：线程栈由调用者声明（`pthread_attr` / 显式传栈），
  内核没有匿名栈池可以分配。

现在**拒绝**这些字段，是为了将来真做的时候能安全地做——那时把拒绝改成接受，
旧记录的语义不会漂移。

### 4.5 校验

内核按顺序检查，任一步失败即整体回退到编译期默认：

| 码 | 名称 | 含义 |
|---|---|---|
| 0 | OK | 记录有效 |
| 1 | `ERR_MAGIC` | 不是 `"SCFG"`（多半是空白扇区） |
| 2 | `ERR_VERSION` | 版本不认识 |
| 3 | `ERR_CRC` | CRC 不符（写了一半掉电） |
| 4 | `ERR_HW` | `hw_compat_id` 与本机不符 |
| 5 | `ERR_MODE` | `mode` 不是 0/1 |
| 6 | `ERR_COUNT` | `slot_count` 越界 |
| 7 | `ERR_SLOT_TYPE` | 槽位类型不是 1/2 |
| 8 | `ERR_SLOT_RANGE` | 槽位落在池外 |
| 9 | `ERR_SLOT_SIZE` | 槽位长度不合法 |
| 10 | `ERR_SLOT_ALIGN` | 槽位没过对齐要求 |
| 11 | `ERR_SLOT_OVERLAP` | 槽位互相重叠 |
| 12 | `ERR_SLOT_RAM` | RAM 窗口落在 `SLOT_RAM` 之外 |
| 13 | `ERR_SLOT_COUNT_MAX` | 槽位数超过 `SVCRT_CFG_SLOT_MAX` |
| 14 | `ERR_RECLAIM` | `reclaim_mode` 不认识 |
| 15 | `ERR_KNOB` | 运行期参数超范围（如 `boot_delay_ms` 超过上限） |
| 16 | `ERR_NOT_IMPL` | 要求了这份固件没有的代码路径 |
| 17 | `ERR_RESERVED` | 保留字段/未知位非 0 |
| 18 | `ERR_SLOTS_IN_MODE` | 该模式下不该出现的槽位表 |

**配置无效不是错误，是回退**：内核照常启动，用编译期默认布局，
并在 `cfg show` 里把 `record : none` 显示出来。

## 5. 裸镜像与开发槽位表

"用 Keil 直接下载 App 并下断点"这条路走的是**裸镜像**：没有 256 字节镜像头、
没有 CRC，与安装路径的 `.svcapp` 是两种格式。

扫描器无法从裸镜像的内容里推断"它是什么类型、占几个扇区"，所以必须由
`config/svcrt_partition.h` 第八节显式声明一张表：

```c
#define SVCRT_DEV_SLOT_MAX   (4)
#define SVCRT_DEV_SLOT0_UNIT  (0)   /* 起始扇区单元 */
#define SVCRT_DEV_SLOT0_UNITS (1)   /* 占几个扇区 */
#define SVCRT_DEV_SLOT0_TYPE  (2)   /* 1=App, 2=驱动, 0=该条目不用 */
...
```

F427 出厂配置：槽 0/2 是驱动、槽 1/3 是 App，各占一个扇区。
`app_demo` 烧在 `0x08060000`（池基址 + 1 个扇区 = 单元 1），所以它命中 SLOT1，
RAM 窗口 = `0x20010000 + 1 × 16 KB` = `0x20014000`，与 `build/app_demo.sct`
里的 `RW_IMG 0x20014000` 以及 `ARM_LIB_STACK 0x20018000` 完全吻合。

### 5.1 两层开关

| 层 | 开关 | 作用 |
|---|---|---|
| 编译期 | `APP_ALLOW_RAW_IMAGE` | 决定这段代码**在不在**固件里。发布固件置 0，只认带 CRC 的 `.svcapp` |
| 运行期 | `flags` 的 `RAW_ALLOW` 位 | 决定这台设备**走不走**裸镜像旁路 |

两层的语义是"能力"与"策略"：编译期关掉就是没有这条路；
编译期开着但运行期关上，则这台设备按签名镜像办事。

### 5.2 认领规则

内核在**带头镜像扫描之后**才认领开发槽位，顺序不能反：开发槽位落在池底，
而安装器也从池底往后分配，一个"装进去的带头镜像"完全可能正好落在开发槽位里。
先认领会把这种镜像整段当成裸镜像，带电位的那 256 字节镜像头就再也认不出来。

认领时跳过三类区间：

1. 基址处是 `SVCRT_APP_MAGIC` 的（有镜像头，交给带头扫描）；
2. 已被带头镜像登记的（头尾各查一次，防跨边界）；
3. 整段全 `0xFF` 的（空槽不算镜像）。

认领成功后内核做两件事：**绑定 §2.1 的 RAM 窗口**，并按 `APP_AUTO_START` /
`DRIVER_AUTO_START` 置自启标志。

### 5.3 裸镜像不参与回收

裸镜像登记的槽位状态是 `SVCRT_APP_SLOT_RAW`（值 5），不是 `LOADED`（值 1）。
压实与回收只搬 `LOADED`，所以裸镜像**不会被搬走、不会被擦**；
`uninstall` 也会明确拒绝裸镜像（`SVCRT_LOADER_ERR_STATE`）——
开发者直接烧进池里的东西，内核不能替它决定"哪段属于它"。

任务停止后，内核按"基址处有没有镜像头"把它退回 `RAW`，
免得它落成 `LOADED` 之后被下一次压实搬走。

## 6. 怎么用

### 6.1 上位机写配置

工具：`tools/svcrt_layout.py`。它和内核共用同一份 `config/svcrt_partition.h`
作为参数来源，不需要手工抄地址。

```bash
# 1) 生成一份模板（fixed 模式，槽位按编译期开发槽位表展开）——打印到 stdout
python tools/svcrt_layout.py template --mode fixed \
    --pool-base 0x08040000 --sector 0x20000 > layout.json

# 2) 校验（越界 / 重叠 / 扇区对齐 / RAM 窗口都会在这里报出来），不落盘
python tools/svcrt_layout.py check --json layout.json

# 3) 落成 512 字节记录 + 每个槽位的 .sct
python tools/svcrt_layout.py build --json layout.json \
    --bin layout.bin --sct-dir build/fixed_slots

# 4) 需要的话顺带导出可贴进 config/svcrt_partition.h 的默认槽表片段
python tools/svcrt_layout.py build --json layout.json --emit-header
```

子命令只有四个：`show`（打印编译期回退布局）、`template`（打印示例 JSON）、
`check`（校验，不写任何东西）、`build`（校验并产出记录）。
`--config` / `--header` 可选，默认读 `config/svcrt_partition.h`——两块板的差异
全部由这份头文件决定，工具不自己算地址、也不允许手抄。

`layout.bin` 有两条落地路径：

1. **烧录器**直接写到 `CONFIG_BASE`（F427 上是 `0x08020000`）。工具输出的就是
   扇区开头的 512 字节，**写之前不需要擦整个扇区**；但如果该扇区此前写过别的
   东西，仍应先擦除。
2. **串口在线写入**（`tools/svcrt_cfg.py`），不必拆板、不必烧录器，见 §6.3。

图形界面的等价入口见 `tools/svcrt_host_gui.py`（§6.6），它把本节与 §6.3、
§6.4 的操作都做成了按钮。

### 6.2 设备端查看与操作

串口控制台（`ark>`）：

```
cfg show      # 当前生效的模式、来源、槽位表、运行期参数、记录校验结果
cfg load      # 进入接收状态，等待上位机把 512 字节记录发下来（见 §6.3）
cfg clear     # 擦掉 CONFIG 扇区，回退到编译期默认
```

> **`cfg load` 不是「重新读一遍配置」**。配置区是启动时读的，要重新读就重启。
> `cfg load` 的实际语义是**接收**：它打印就绪行后进入接收循环，把上位机发来的
> 4×128 字节拼成一条记录，校验通过才写进 CONFIG 扇区，并把判决用流控字节
> （`0x06` 继续 / `0x15` 停止）回给主机。手动在终端里敲 `cfg load` 只会等到
> 5 秒超时然后回 `cfg load: timed out waiting for the record`。

`cfg show` 的典型输出（AUTO，配置区无记录）：

```
layout    : auto (source: compile-time default)
config    : 0x08020000 +128K, 256 record(s) per sector
reclaim   : global
knobs     : log 3 (record 0), restart max 3
boot      : hold 0 ms before autostart, raw images refused
record    : none, compile-time default in use
```

`cfg show` 的典型输出（FIXED，记录来自配置区，带槽表）：

```
layout    : fixed (source: device config region)
config    : 0x08020000 +128K, 256 record(s) per sector
reclaim   : none
knobs     : log 3 (record 0), restart max 3
boot      : hold 0 ms before autostart, raw images refused
record    : accepted

slot  type  base        size     ram         auto
 0    app   0x08040000  131072   0x20010000  1
 1    drv   0x08060000  131072   0x20011000  1
```

`source` 只有两种取值：`compile-time default`（配置区没有有效记录，或有记录但
校验不过时回退）、`device config region`（用了配置区里的记录）。
`reclaim` 在 FIXED 模式下恒为 `none`——固定槽位从不压实，谈回收力度没有意义。

### 6.3 串口在线写入配置（`tools/svcrt_cfg.py`）

```bash
python tools/svcrt_cfg.py show  --port COM3
python tools/svcrt_cfg.py write --port COM3 --config layout.json
python tools/svcrt_cfg.py clear --port COM3
```

512 字节记录超过 shell 行缓冲（128 字节），所以走二进制分块而非命令行参数：
4 块 × 128 字节，每块之后设备回一个流控字节；**最后一块的流控字节就是判决**。
设备拒绝时会在同一个串口先打印原因行（如 `bad magic` / `bad crc`），工具**原样
转发**，不替设备猜原因。

写协议上有三个必须遵守的约定，任何一条破了都会得到「设备收到 512 字节却报
`bad magic`」这种指向错误方向的症状：

| 约定 | 原因 |
|---|---|
| 命令用 **CR** 结尾（`cfg load\r`），不要 CRLF | shell 以 CR 断行，CRLF 多出的 LF 会留在接收 FIFO 里，把整条记录顶偏 1 字节 |
| 设备在**打印就绪行之前**清空接收 FIFO | 上面的残留字节必须在这里丢掉；顺序不能颠倒，否则会把主机看到就绪行后立刻发来的第一块一起吃掉 |
| 主机等**整套横幅**（或一段静默）再发第一块 | 设备在打印 `ready` 之后还在打印两行，只看关键字 `ready` 会撞进最危险的窗口 |

失败时的读法是：**先怀疑流的起点，再怀疑内容**。整条记录被顶偏一字节和内容
全错的设备侧表现完全一样（都只能在最后的 magic 校验里报错）。

### 6.4 生效范围与重启

`cfg load` / `cfg clear` 之后设备会提示重启——这不是保守，是因为记录里写的是
**布局策略与运行期参数**：

| 什么时候生效 | 项目 |
|---|---|
| 立即生效 | 日志级别（`svcrt_log_set_level` 当场调用） |
| **重启后**才完全一致 | 安装模式（`fixed` / `auto`）、槽位表、回收力度、分区几何、RAM 窗口 |

原因是池扫描与镜像启动都在启动早期按当时的布局做完了。改完策略不重启，设备会
处于「`cfg show` 说新布局、装载路径按旧布局」的分裂状态——**装进去的落点会和
你以为的不一样**。

### 6.5 真机验收结论（F427）

- `write`（4×128 分块）→ 设备 `cfg load: ok, record N`，读回 `source: device config region`、
  `reclaim minimal`、`knobs log 4 / restart max 5`；
- 坏 CRC 记录被拒，设备给出真实原因 `bad crc`，且**已有的有效记录不受影响**；
- `fixed` 记录写入并重启后：`cfg show` 报 `fixed`，`pool` 列出配置里的两个固定槽，
  共享分区表直读 `layout_mode = 1`（`0x20000000 + 52`，u32 小端）与之一致；
- `clear` 后回 `auto (source: compile-time default)`、`record : none`。

> **一个状态一个真相源。** 布局的权威副本在**共享分区表**（`svcrt_layout_init()`
> 从配置区采用后 `publish()` 进去），加载器判 `FIXED` 读的就是它。池扫描曾经用
> `svcrt_ptable_init()` 清槽位表，把这张表整片重新播种成编译期默认值，于是
> 「配置里写了 fixed，装载路径却按 auto 走」——查询命令读的是布局模块自己的
> 状态，所以看起来一切正常。现在扫描只调 `svcrt_ptable_clear_slots()`。
> 改这一带代码时请守住这条线：**复位「一类记录」不要用「整表重新播种」**。

### 6.6 图形界面上位机

```bash
python tools/svcrt_host_gui.py            # 需要 pyserial；tkinter 随 Python 自带
```

四个页签：**连接**（扫串口、开关）、**控制台**（敲 shell 命令、看回显）、
**安装**（选 `.svcapp`、看进度与设备判决）、**布局配置**（`show` / `write` / `clear`
与模板生成）。

### 6.7 给客户二次开发的推荐组合

```
mode          = fixed
slot[0..3]    = 按 config 第八节的开发槽位表
flags         = RAW_ALLOW
boot_delay_ms = 0（或留几百毫秒给调试器挂接）
```

这样客户拿到的是一台"每个槽位地址固定、可以直接用 Keil 往固定地址灌代码、
灌完就能下断点"的板子，而不需要理解池、压实、回收这些概念。
发布版固件则把 `mode` 改成 `auto`、`flags` 清 0，只接受带 CRC 的 `.svcapp`。

## 7. 相关文件

| 文件 | 角色 |
|---|---|
| `config/svcrt_partition.h` | **全工程唯一地址源头**；分区、池、开发槽位表、编译期默认布局 |
| `config/stm32f401/svcrt_partition.h` | F401 版本，形状相同、尺寸不同 |
| `kernelsrc/include/svcrt_layout_def.h` | 配置记录的二进制布局（C 侧） |
| `kernelsrc/include/svcrt_layout.h` | `svcrt_layout_*` 访问器 |
| `kernelsrc/src/svcrt_layout.c` | 读记录、校验、发布到共享内存分区表 |
| `kernelsrc/src/svcrt_loader.c` | 扫描、认领、启动、压实、卸载 |
| `kernelsrc/src/svcrt_ptable.c` | 分区表与伙伴分配器 |
| `tools/svcrt_layout.py` | 上位机：模板 / 校验（`check`）/ 落盘 / `.sct` / 头文件片段 |
| `tools/svcrt_cfg.py` | 上位机：经串口 `show` / `write` / `clear` 设备端配置区 |
| `tools/svcrt_host_gui.py` | 图形界面：连接 / 控制台 / 安装 / 布局配置四个页签 |
| `tools/gen_scatter.py` | 生成 `.sct`（**构建产物，不要手工编辑**） |

> `.sct` 一律由 `tools/gen_scatter.py` 生成。手工改过的 `.sct` 在下次编译时
> 会被覆盖，而且它和内核的推导结果会悄悄分叉——那种 bug 表现为
> "编译通过、下载成功、运行跑飞"。
