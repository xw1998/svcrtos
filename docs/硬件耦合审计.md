# SVCrtOS 硬件耦合审计

审计对象：`kernelsrc/`（内核）、`board/`（板级）、`config/`（布局）、`example/`（工程）
审计手段：`_nova/w2_audit.py` 扫描 include 关系、跨层符号、HAL/外设令牌、uvprojx include 路径
审计日期：2026-09-22

---

## 一、结论

| 档位 | 项 |
|---|---|
| **达标** | 内核源码零芯片头依赖；内核到板级只有一个注入点（`SVCRT_BOARD_CONFIG`）；port 层依赖面收敛到 3 个头；App / 驱动工程不引用 `board/`、`port/` |
| **待修（3 项，见 §四）** | `svcrt_guard.c` 无用 include 板级头；`SVCRT_SYSTEM_CLOCK_HZ` 是死宏且值不真实；F401 内核工程借用 F427 的 HAL 源码目录 |
| **结构性解耦（与功能解耦一并做）** | `svcrt_fs.c` 直接绑 `svcrt_blk` + `svcrt_partition.h`，无法单独移植（见 §六） |

一句话：**内核层没有硬件知识泄漏，硬件知识集中在 `board/<chip>/`；需要清理的是三处零散残留，以及一处挡在文件系统独立化路上的概念绑定。**

## 二、三方依赖矩阵

| 方向 | 现状 | 判定 |
|---|---|---|
| 内核 → 芯片头（`stm32f4xx.h` / `core_cm4.h`） | **0 处** | 达标 |
| 内核 → 板级头 | 1 处：`svcrt_guard.c` include `svcrt_board_config.h` | 待修（冗余） |
| 内核 → 板级宏注入点 | 3 处，均为 `#include SVCRT_BOARD_CONFIG`：`svcrt_config.h`、`port/arm/cortex-m3|cortex-m4/svcrt_port.c` | 合规（设计如此） |
| board → 内核契约头 | 每个驱动 include `svcrt_hal.h` / `svcrt_dev.h` / `svcrt_types.h` 等 | 合规（board 是 HAL 契约的实现方） |
| board → 分区头 | `drvflash.c`（只用 `CHIP_FLASH_BASE/SIZE`）、`drvblk.c` | 合规但可优化（见 §四.3） |
| board → port 内部函数 | 调 `svcrt_port_flash_erase/write/sector_size` | 合规（这三个声明在 `svcrt_hal.h`，属契约面） |
| port → 内核 | 只 include `svcrt_config.h` / `svcrt_hal.h` / `svcrt_task.h` | 达标 |
| App / 驱动工程 → 硬件目录 | uvprojx 的 include 路径中**无** `board/`、`port/` | 达标 |

## 三、内核中的"硬件知识"扫描

按 HAL / 外设令牌（`HAL_*`、`GPIOx`、`USARTn`、`SysTick`、`NVIC`、`SCB`、`DWT`、`ITM`）扫描 `kernelsrc/`：

| 文件 | 命中 | 判定 |
|---|---|---|
| `port/arm/cortex-m3|cortex-m4/svcrt_port.c` | MPU / SysTick / SCB | 架构层职责，达标 |
| `include/svcrt_arch.h`、`svcrt_mpu.h`、`svcrt_fault.h`、`svcrt_task.h` | `MPU` 字样 | 是"有没有 MPU 能力"这类术语，不是寄存器操作，达标 |
| `components/mdk_trace/*` | DWT / ITM | trace 天然依赖调试硬件；**需要能被整块关掉**（见 §五） |
| `components/cm_backtrace/*` | NVIC / DWT | 同上 |
| `sdk/driver_sdk/examples/example_i2c_drv.c`、`example_spi_drv.c` | `I2C1` / `SPI1` | 示例驱动，属性应在 board 侧；仅示例代码，记录 |
| 其余命中 | 中文注释里提到 board 路径 | 非依赖 |

**没有一处寄存器级操作出现在 `kernelsrc/src/` 的通用逻辑里。**

## 四、待修清单

### 1. `kernelsrc/src/svcrt_guard.c:15` —— 内核反向 include 板级头

```c
#include "svcrt_board_config.h"
```

全文件 grep `board_config` / `BOARD_` 只有这一行命中，**它没有使用板级配置里的任何符号**，是一处冗余 include。内核源码出现板级头会让人误以为 guard 依赖板级事实，直接删除。

（`svcrt_guard.c` 真正需要的是心跳合同 `SVCRT_GUARD_*`，来自 `svcrt_guard.h`。）

### 2. `SVCRT_SYSTEM_CLOCK_HZ` —— 死宏，且值不真实

| 位置 | 值 |
|---|---|
| `kernelsrc/include/svcrt_config.h:277`（`#ifndef` 兜底） | 168 000 000 |
| `board/stm32f427/svcrt_board_config.h:16` | 168 000 000 |
| `board/stm32f401/svcrt_board_config.h:18` | 84 000 000 |

事实：**内核不读这个宏**。`svcrt_port_get_system_clock()` 的实现是 `return (uint32)SystemCoreClock;` —— 频率的唯一有效来源是 CMSIS 的 `SystemCoreClock`，由 board 的时钟初始化函数设置。F427 板上实测 `SystemCoreClock = 96 MHz`，而宏写 168 MHz（器件名义上限），两者差 1.75 倍。

处置：**删除该宏的三处定义**，在 `svcrt_config.h` 的对应位置留注释说明"系统频率唯一来源是 `SystemCoreClock`，不要再引入编译期频率宏"。这样主机侧换算只认 `config/mdk_trace_config.h` 的 `MDK_TRACE_CPU_HZ`，不会有人从板级宏抄错值。

### 3. F401 内核工程借用 F427 的 HAL 源码目录

`example/stm32f401/kernel/SVCRTOS_TEST/MDK-ARM/SVCRTOS_TEST.uvprojx` 的 include 路径含：

```
../../../../stm32f427/kernel/SVCRTOS_TEST/Drivers/STM32F4xx_HAL_Driver/Inc
../../../../stm32f427/kernel/SVCRTOS_TEST/Drivers/CMSIS/Include
```

即 F401 工程跨芯片目录取 F4 公共 HAL 与 CMSIS。功能上没问题（F4 系列 HAL 同源），但它意味着"加第三个芯片时要再复制一份"。记录在案，本轮不改（改动会触及 MDK 工程文件与 HAL 树，风险大于收益）。

## 五、耦合分层原则（本轮确立，写入规范）

四层各管一件事，跨层引用必须显式：

| 层 | 回答的问题 | 唯一载体 | 谁可以提供 |
|---|---|---|---|
| **能力层** capability | 这块板/这颗芯片**有什么** | `board/<chip>/svcrt_board_config.h` + CMSIS | 硬件事实；内核只读不写默认值 |
| **选配层** feature | 这次构建**要哪些功能** | `kernelsrc/include/svcrt_features.h` | 团队/项目；每个开关必须能被关掉且关掉后能编译 |
| **契约层** contract | 内核要求硬件**提供什么接口** | `kernelsrc/include/svcrt_hal.h` | 内核定义，board 实现 |
| **布局层** layout | 东西**放在哪个地址** | `config/svcrt_partition.h` | 全工程唯一地址源头 |

判定规则：

- 内核源码（`kernelsrc/src/`、`kernelsrc/include/`）**只允许**通过 `SVCRT_BOARD_CONFIG` 一个口子接触能力层；
- 每次新增功能，先问它属于哪一层。属于选配层的功能**必须**在 `svcrt_features.h` 里有开关；
- 关掉一个开关后，`kernelsrc` 必须仍能编译通过（这条由 CI 门禁的裁剪构建检查逐步落地）。

## 六、与后续工作的衔接

### `svcrt_fs.c` 的概念绑定（VFS 独立化的输入）

`kernelsrc/src/svcrt_fs.c` 同时 include：

```c
#include "svcrt_blk.h"        /* 块设备 —— 合理，FS 需要它 */
#include "svcrt_partition.h"  /* 分区布局 —— 不合理，FS 不该知道机内布局 */
#include "lfs.h"              /* 绑定单一文件系统实现 */
```

它把"VFS 抽象 + littlefs 实现 + 块设备 + 机内分区"四件事写在一个文件里。要做独立的 `ark_vfs` 项目，需要切成：

```
ark_vfs（独立项目，零 RTOS/零硬件依赖）
  ├── vfs 核心       挂载表 / vnode / file / 路径解析 / 文件系统类型注册
  ├── fsdrv          各文件系统实现（littlefs、ramfs、devfs…）
  └── backend        块设备接口（read/prog/erase/sync）、字符设备接口
SVCrtOS 侧（port）
  ├── 块设备后端：svcrt_blk → ark_vfs 的 block backend
  ├── 锁与内存注入：svcrt 的 mutex / malloc
  └── 分区布局：由 SVCrtOS 在挂载时把 (dev, offset, size) 传进去，VFS 不读分区头
```

即：**分区知识留在 SVCrtOS 侧，VFS 只认"一个起始地址 + 长度"的块设备。**

### 内核当前的分区头引用面

`kernelsrc/` 中 include `svcrt_partition.h` 的有 12 个文件：
`svcrt_config.h`、`shell/platform_svcrtos.c`、`shell/svcrt_shell.c`、`svcrt_audit.c`、`svcrt_crash.c`、`svcrt_fs.c`、`svcrt_installer.c`、`svcrt_layout.c`、`svcrt_loader.c`、`svcrt_mpu.c`、`svcrt_ptable.c`、`svcrt_task.c`。

其中 11 个**本来就该知道布局**（加载器、安装器、分区表、MPU 窗口、崩溃日记落点、共享内存），属于设计意图。唯一的例外是 `svcrt_fs.c` —— 它是"文件系统"而不是"布局管理"，属于 §六 要切断的那条。
