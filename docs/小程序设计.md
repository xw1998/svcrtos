# 小程序：放在文件系统里的第三种用户态应用

> **验证状态**：F427 已**上板验证**（2026-09-23，hw `0x42700005` / ABI v9），
> 逐项记录见 §9；F401 只做编译（该板关掉了 `SVCRT_USE_MINIAPP`）。

小程序（MiniApp，镜像头 `type = 3`）要解决的问题只有一个：
**有些程序不值得为它做一次"安装"**。它就以一个普通文件的形式躺在文件系统里，
想跑的时候被 load 进 RAM 执行，退出后 RAM 立刻归还；再跑就再 load 一遍——
用一点效率换掉"分区 / 槽位 / 版本 / 安装窗口"这一整套手续。

## 1. 三种用户态应用的关系

| 项 | App | 驱动 | 小程序 |
|---|---|---|---|
| 镜像类型 | `type = 1` | `type = 2` | `type = 3` |
| 常驻位置 | Flash 镜像池（一个槽位） | Flash 镜像池（一个槽位） | **文件系统里的一个文件** |
| 落点 | 安装时由加载器决定，固定到卸载 | 同 App | **每次运行现借 RAM，退出即还** |
| 代码执行方式 | XIP（Flash 原地执行） | XIP | **搬进 RAM 执行**（无 XIP） |
| 安装手续 | 需要（`install` 窗口 + 版本把关） | 需要 | **不需要** |
| 内存占用 | Flash 里一份 + 声明的 RAM 块 | 同 App | **RAM 里代码块 + RAM 块两块** |
| 启动命令 | `app start <slot>` | `drv start <slot>` | `mini run <path>` |
| 上限 | 池可用空间 | 池可用空间 | 代码块 ≤ `SLOT_RAM_MAX_BLOCK`（默认 32 KB） |

容器是同一个：256 字节镜像头 + 重定位表 + 负载，入口约定一致
（`APPSTART` / `DRVSTART` / `MINISTART` 都是"跳到 C 运行时 `__main`"的桩），
`svcrt_oslib.c` 这一份 SVC 门面三方共用。差别只在镜像头的 `type` 字段
与它决定了哪条装载路径。

## 2. 内存模型：两块，不是一块

一次装载向 RAM 池借**两块** 2 的幂对齐的块（都在 `SLOT_RAM_BASE` 起、
总量 `SLOT_RAM_TOTAL` 的那片池子里）：

| 块 | 大小 | 内容 |
|---|---|---|
| 代码块 | `pow2_ceil(align8(负载长度))`，下取到 `SLOT_RAM_MIN_BLOCK` | 负载本体，从块基址开始 |
| RAM 块 | 镜像头里声明的 `ram_size`（本身必须是 2 的幂） | RW/ZI，栈从块顶向下切 `APP_TASK_STACK_SIZE` |

两块**同生同死**：先给代码块找地方、把它记进局部占用表，再给 RAM 块找；
任一步失败就整体放弃，不会留下"只借到一块"的中间状态（归还路径只认一种状态）。

### 为什么不是"把两者塞进一个 pow2 块"

第一版就是这么写的，理由是"一个块比两个块省"。这个理由是**错的**：

```
pow2_ceil(代码 + RAM)  ≥  pow2_ceil(代码) + RAM        恒成立
```

因为 `pow2_ceil(代码) ≥ 代码`，而 `代码 + RAM` 又必须上取整到 2 的幂。
最常见的"代码远小于 RAM"的情形下两者接近**翻倍**：

| 代码 | RAM | 单块写法 | 两块写法 |
|---|---|---|---|
| 1 KB | 8 KB | 16 KB | **9 KB** |
| 4 KB | 4 KB | 8 KB | **8 KB** |

单块只在两者非常接近且刚好跨过 2 的幂边界时才不吃亏。两块还顺带把 MPU 拆干净了：
代码窗一个 region、数据窗一个 region，数据窗不必再迁就代码窗的"可执行"属性。

### 与 ELF「占用少」的四条做法对照

| ELF 的做法 | 我们能不能抄 | 结果 |
|---|---|---|
| 按需分页、只映射真正用到的部分 | 不能（无 MMU 的机器没有页机制） | 只能整块搬进 RAM |
| 段映射：代码段留在文件里由 MMU 映射，不占 RAM | 等价物是 XIP；但需求明确要求"load 进内存" | 代码必须占 RAM |
| 头与元数据不常驻 | 能 | 256 字节头 + 重定位表**读完即丢**，不落 RAM |
| 搬运过程不在内存里多留一份 | 能 | 读一段、打一段补丁：负载直接读进代码块基址，**没有中转缓冲**；重定位表压成 4 字节一项 |
| 进程退出释放全部映射 | 能 | 任务退出钩子立刻归还两块 |

所以本方案的占用是**数学下限**：`pow2(负载) + ram_size`。剩下的只有两处
"能省则省"已经在做——头/表不落 RAM、不设中转缓冲。

## 3. 装载流程（六步）

```
1. 读 256 字节头        -> svcrt_loader_check_header(p_rel = 0, 掩码 = MINI)
2. 读重定位表            reloc_count * 4 字节，进静态表（4 KB = 1024 项上限）
                         再 check_header 一次（这次带表）：两遍都过才继续
3. 尺寸校验              code_want = pow2_ceil(align8(image_size))
                         超上限 / RAM 不是 2 的幂 / ram_size < 栈  -> ERR_SIZE
                         code_want < code_size（回绕自证）        -> ERR_SIZE
4. 借块                  svcrt_ptable_mini_alloc()：代码块 + RAM 块
5. 搬负载 + 打补丁       按 256 字节分段读，先算标称 CRC，再过重定位表
6. 起任务                入口 = 代码块基址 + entry_offset（带 Thumb 位）
                         栈顶 = RAM 块顶；TCB 四个窗口字段回填；构建 MPU
```

装载全程持调度器锁，并且用一个自旋锁保护的 `busy` 标志挡住并发——**同一时刻
只允许一个小程序**。理由不是"没内存"，而是两个小程序会互相覆盖代码区，
那种错现场查不出来。

停止的顺序也不能反：**先把镜像（含它创建的线程）踢出调度，再归还块**；
反过来的话块可能立刻被下一个装载者拿去写代码，而原任务还在跑。

## 4. 体积上限：可以在运行期收紧，不能放宽

| 层 | 值 | 说明 |
|---|---|---|
| 编译期天花板 | `SLOT_RAM_MAX_BLOCK`（F427 = 32 KB） | 同时是池单块物理上限、App 镜像校验上限、MPU 数据窗口上限 |
| 运行期上限 | 默认 = 天花板，可 `mini limit <bytes>` 收紧 | 越界报 `PARAM`，**不夹取** |

**为什么只能收紧**：放宽会让 `svcrt_mpu_ram_window()` 的判定落到"内核 RAM 兜底
窗口"分支——那是一种会**静默**把任务放进错误窗口的失败。不该由一次调参触发。
要真正抬高天花板，得改 `SLOT_RAM_MAX_BLOCK` 并同时满足池与 MPU 的静态断言。

**为什么不夹取**：夹取会把"我设了 64 KB 却拿到 32 KB"变成一句看不出来的谎话。
超出范围直接报 `SVCRT_LOADER_ERR_PARAM`。

**为什么不做持久化**：写进设备配置区要动配置记录的 ABI（版本 1 -> 2、
腾 `reserved` 字段），会让板上已有记录失效。本轮只做运行期（shell + 内核 API）。
要让它在重启后仍然生效，得走配置记录升级这条路——那是另一件事。

## 5. 怎么用

打包走的是**和 App 完全相同的四遍差分链接流水线**（标称 / ROM+delta /
RAM+delta / 双 delta 验证），只在类型上区分：

```bash
py -3 tools/pack_app.py --project example/stm32f427/app_sdk/MINI_DEMO/MDK-ARM/mini_demo.uvprojx \
        --type miniapp --name MINI_DEMO --ram-size 8192 --out build/mini_demo.svcapp
```

打包期会顺手拦下两类"打完也跑不起来"的镜像：

- 重定位表项数 > `SVCRT_APP_RELOC_MAX`（内核装载器不做滑动窗口，超限读不完表）；
- 代码块 > `SLOT_RAM_MAX_BLOCK`，或 代码块 + RAM 块 > `SLOT_RAM_TOTAL`。

放进设备文件系统（`fs put` 的接收窗口，主机侧是 `tools/fs_put.py`）：

```bash
py -3 tools/fs_put.py --port COM3 --path /mini_demo.app build/mini_demo.svcapp
```

（文件系统没有 `mkdir` 命令，路径就用卷根下的文件名；README 里的 `/mini/...`
只是"以后有了目录"的示意。）

运行与观察：

```
mini run /mini_demo.app          # 装载并启动
mini stat                        # 看当前在跑的小程序：任务号/两块基址与大小/入口/CRC/上限
mini limit                       # 看当前上限与默认值
mini limit 8192                  # 把上限收紧到 8 KB
mini stop                        # 停掉并归还两块
```

## 6. shell 命令与错误码

| 命令 | 语义 |
|---|---|
| `mini` / `mini stat` | 打印状态；没在跑时打印"无"与当前上限 |
| `mini run <path>` | 装载并启动；路径是文件系统卷内的绝对路径 |
| `mini stop` | 停掉并归还两块 |
| `mini limit [bytes]` | 不带参数看上限；带参数收紧（0 = 恢复默认） |

错误码沿用加载器那一套（`kernelsrc/include/svcrt_loader.h`），只多一个本路径独有的：

| 码 | 含义 |
|---|---|
| `SVCRT_LOADER_ERR_MAGIC` / `COMPAT` | 不是有效镜像 / `hw_compat_id` 不符 |
| `SVCRT_LOADER_ERR_SIZE` | 尺寸不合格：超上限、RAM 不是 2 的幂、装不下栈、或长度回绕 |
| `SVCRT_LOADER_ERR_CRC` | 头 CRC 或负载 CRC 不符 |
| `SVCRT_LOADER_ERR_RELOC` | 重定位表不合法（含"补丁回退"这种自相矛盾的表） |
| `SVCRT_LOADER_ERR_NOSPACE` | 池里借不到两块（不是"没有内存"的意思，是碎片或已被别人占了） |
| `SVCRT_LOADER_ERR_BUSY` | 已经有一个小程序在跑 |
| `SVCRT_MINI_ERR_FS`（-18） | 读文件失败，原因看 `svcrt_fs_last_error()` |

## 7. 已知限制（如实列出）

1. **故障策略与槽位镜像不同**。小程序的主任务不属于任何槽位，所以
   `svcrt_loader_on_fault()` 对它返回 -1，连续故障按**内核任务的默认策略重启**，
   不会像槽位镜像那样被"禁用 / 卸载"。也就是说：一个会反复崩的小程序会反复重启，
   需要人工 `mini stop`。要让它也进入"崩溃 N 次就禁用"的体系，得给小程序做一个
   独立的故障计数位——本版没做。
2. **代码窗口可执行且可写**。小程序跑在自己的代码块里，MPU 给的是
   `RAMX`（非特权 RW + 可执行），也就是**它可以在自己的块内自修改**。
   这与 App 是同一姿态（App 也在自己的 ROM 窗口里执行），
   而小程序退出即释放，所以本版按"姿态放宽"记录，而不是当作漏洞处理。
3. **上限只能收紧**，天花板是编译期的 `SLOT_RAM_MAX_BLOCK`（见 §4）。
4. **同一时刻只有一个小程序**（见 §3）。

## 8. 目录与文件

| 路径 | 作用 |
|---|---|
| `kernelsrc/include/svcrt_mini.h` | 门面：run / stop / info / 上限读写 / 退出钩子 |
| `kernelsrc/src/svcrt_mini.c` | 六步装载、两块记账、上限判定 |
| `kernelsrc/src/svcrt_ptable.c` | `svcrt_ptable_mini_alloc / mini_free / mini_info`（两块同生同死） |
| `kernelsrc/shell/svcrt_shell.c` | `mini` 一族命令 |
| `kernelsrc/sdk/mini_sdk/` | 小程序 SDK：`MINISTART` 桩、`main()` 骨架（oslib 与 App 共用） |
| `example/stm32f427/app_sdk/MINI_DEMO/` | 示例工程（跑三轮心跳后退出，用来观察两块回收） |
| `tools/pack_app.py --type miniapp` | 打包（四遍差分 + 重定位表） |

设备侧开关是 `SVCRT_USE_MINIAPP`（`kernelsrc/include/svcrt_features.h`，默认开），
它依赖 `SVCRT_USE_FS`。**F401 板已在板配置里关掉它**：那颗芯片的内核 RAM 只有
56 KB，装载器里 4 KB 的静态重定位表链接器放不下（实测 47 个 `L6406E`）。

### 9.1 上板实测逐项

| 项 | 命令 | 实测结果 |
|---|---|---|
| 上限读数 | `mini limit` | `32768 B (default 32768 B, range 1024..32768 B)` |
| 装载并运行 | `mini run /mini_demo.app` | 996 B 负载 -> 代码块 1024 B @ `0x20011000`、RAM 块 8192 B @ `0x20016000`、任务 10；小程序三行 `[mini] loop 0/1/2` 真的从控制台出来 |
| 运行中状态 | `mini stat` | `mini running: task 10, code 996 B in 1024 B @ 0x20011000, RW/stack 8192 B @ 0x20016000` |
| 自然退出回收两块 | 打印 `[MINI:491] task 10 returned: MiniApp finished, code and RAM blocks back in the pool` | `mini stat` 后为 `none running`；`pool free` 回到 368292 B，与装载前**逐字节相同** |
| 反复重跑 | 连续 3 次 `mini run` | 每次都重新从文件系统读、重新借两块并跑完（`tick` 分别 25102 / 66114 / 81807 ms） |
| 停止路径 | `mini run` 后紧跟 `mini stop` | `[MINI:400] stopped: task 10, code and RAM blocks returned to the pool`，两块归还 |
| 上限收紧 | `mini limit 1024` 后 `mini run` | 运行被拒 `rc=-4`（`SVCRT_LOADER_ERR_SIZE`），并提示 `size limit: 1024 B now` |
| 上限不夹取 | `mini limit 5000` / `mini limit 99999` | 都拒收 `rc=-1`（`SVCRT_LOADER_ERR_PARAM`），提示 `need a power of two in 1024..32768 B`，**没有**被悄悄改成 4096 或 32768 |
| 恢复默认 | `mini limit 0` | 回到 32768 B |
| 文件不存在 | `mini run /nope.app` | `rc=-18`（`SVCRT_MINI_ERR_FS`），随行给出设备侧真实原因 `file system: -2 (LFS_ERR_NOENT)` |
| 并发拒绝 | 运行期再发一次 `mini run` | `rc=-15`（`SVCRT_LOADER_ERR_BUSY`），不覆盖正在跑的那个 |

上板用的镜像是 `build/mini_demo.svcapp`（1308 B，负载 996 B，重定位表 14 项），
写进文件系统的路径是 `/mini_demo.app`，用 `tools/fs_put.py` 送进去。
收尾时 `mini stat` = none running、`pool free` = 368292 B（与基线一致），
文件系统里 `mini_demo.app 1308` 仍在。
