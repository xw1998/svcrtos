# 调度器说明

调度器是内核里唯一一个**每个节拍都要跑、每次阻塞/唤醒/抢占也都要跑**的模块。本文说明它的模型、这一轮把就绪集改成 O(1) 的做法与等价性依据、实测到的切换开销，以及还没做的部分。

源码：`kernelsrc/src/svcrt_task.c`（调度主体、就绪集/延时链、节拍处理）、`kernelsrc/src/svcrt_cfg.c`（任务注册）。

---

## 1. 模型

| 项 | 取值 / 语义 |
|----|------|
| 策略 | **优先级抢占** + 同优先级**时间片轮转** |
| 优先级 | `1..254`，**数值越小越紧急**。`255` 是"无候选"哨兵，不是合法优先级，创建时显式拒绝而不是静默钳制 |
| 任务上限 | `SVCRT_TASK_MAX_NUM = 48`（静态 TCB 数组），其中内核自带与示例静态任务预留 `SVCRT_TASK_MAX_KERNEL = 8` |
| 节拍 | `SVCRT_TICK_PERIOD_US = 500`（2 kHz）。所有超时以毫秒对外，内部按节拍折算 |
| 时间片 | `SVCRT_TIME_SLICE_TICKS = 10`（= 5 ms），只对**同优先级多任务**生效 |
| 任务状态 | `INVALID` / `READY` / `RUNNING` / `WAIT` |
| 候选集 | `READY` 与 `RUNNING` 都算"可运行"——正在跑的任务本身也要参与比较，否则它会在自己身上"输掉"选择 |
| 同优先级裁决 | 就绪链是**环形**链表，队首即被选中者；时间片到点把队首转到队尾 |
| 所有任务都不可运行时 | 返回 `-1`，由调用方走 idle |

### 1.1 三种调度触发点

| 触发 | 位置 | 行为 |
|------|------|------|
| **抢占**（更高优先级就绪） | 各唤醒点（信号量/互斥量/队列/事件/软定时器/装载器唤醒任务）调用 `SVCRT_SWITCH_TASK()` | 立即拉 PendSV。PendSV 里用 `svcrt_sched_next()` 的位图取出最高优先级就绪任务，与当前任务不同就切过去——**不必等下一拍** |
| **节拍**（时间片到点 / 延时到期） | `svcrt_kernel_tick_handler()` | 先做延时链到期唤醒，再对当前任务扣 `slice_tick`；归零则把当前任务转到同优先级队尾，然后按需拉 PendSV |
| **主动让出** | 任务调用阻塞接口（`svcrt_task_delay` / 等信号量 / 等队列……） | 摘链 → 置 `WAIT` → `SVCRT_SWITCH_TASK()` |

抢占的判定与节拍用的是**同一个** `svcrt_sched_next()`，两者不会给出不同答案（`svcrt_sched_is_switching()` 可重复调用，这一点在 `SVCRT_USE_FAST_TICK_SWITCH` 的"按需拉 PendSV"里被依赖）。

时间片只影响**同优先级**：`svcrt_ready_rotate()` 在桶里只有一个节点时直接返回，因此"独苗任务"不会每 5 ms 被无谓地转一圈；更高优先级的任务一就绪就会被位图直接取出，不受片长约束。

任务切换点：`SVCRT_SWITCH_TASK()`（PendSV）。调度决策由 `svcrt_sched_next()` 给出。

## 2. 这一轮改了什么：就绪集从全表扫描改成位图 + 链表

### 2.1 数据结构

| 结构 | 内容 |
|------|------|
| `svcrt_ready_map[8]` | 256 位的优先级位图，第 `p` 位 = 1 表示优先级 `p` 有就绪任务 |
| `svcrt_ready_group` | 8 个 32 位字的"非空"位图（二级位图，一次 32 位比较就能挑出非空组） |
| `svcrt_ready_head[256]` | 每个优先级的**双向环形**链表头（存任务下标，`SVCRT_TASK_NIL = 0xFF` 为空） |
| TCB 的 `ready_next` / `ready_prev` | 就绪链前后指针（下标，不是地址） |
| TCB 的 `delay_next` / `delay_prev` / `delay_tick` / `delay_queued` | 延时链（按绝对到期节拍升序的双向链表） |
| TCB 的 `slice_tick` | 当前任务剩余时间片（仅 RUNNING 的有意义） |

优先级位图必须 **256 位**：内核软定时器任务用 `SVCRT_TIMER_TASK_PRI = 200`，远超 31，所以不能用单个 `uint32`。取最高位用 `svcrt_lowbit32()`——**固定 5 步二分**，步数与输入无关，不依赖 CMSIS 的 `__CLZ`（内核源文件不 include CMSIS 头）。

### 2.2 选择路径

```c
int32 svcrt_sched_next(void)
{
    if(首次调度) { svcrt_ready_rebuild(); }     /* 只发生一次，见 §3.3 */
    if(有待恢复任务) { recover_pending(); }     /* svcrt_recover_cnt==0 时整段跳过 */
    return svcrt_ready_top();                   /* 两级位图 + 链表头，常数步 */
}
```

`svcrt_ready_top()` 的成本与任务数、优先级分布**都无关**：两次 `svcrt_lowbit32()` + 一次数组取值。这是"查找算法复杂度"这条要求的落点——旧实现每次选任务都要扫 48 项，逐项比 `status` 和 `priority`。

### 2.3 延时链

原先每个任务带一个 `escape_tick` 倒计时，**每拍扫全表**逐个减。现在改成按**绝对到期节拍**升序的双向链表：

```c
void svcrt_delay_tick(void)
{
    while(链头存在)
    {
        if((int32)(svcrt_kernel_tick - p->delay_tick) < 0) break;   /* 有符号比较，抗回绕 */
        svcrt_delay_unlink(idx);
        if(p->status != SVCRT_TASK_WAIT) continue;                  /* 已被提前唤醒的僵尸节点 */
        ... 唤醒（超时 / 周期补一拍）...
    }
}
```

每拍只处理链头已到期的节点（通常 0 个），均摊 O(1)。**到期判定用有符号差值**比较而不是 `a < b`，所以节拍计数器回绕（约 24.8 天）不会让任务卡死。

**插入排序必须用同一把尺子（2026-09-23 上板实测修正）**：`svcrt_delay_link()` 原先按 `delay_tick <= t` 做**无符号**比较，而到期判定是**有符号**差值——两者只在回绕处不一致：一个在回绕前不久武装的截止时间数值很小（例如 `0x24`）却仍是“最远”的，无符号排序会把它插到链头，于是它后面所有更早到期的睡眠任务全被挡住，直到它自己到期（最长约一个周期）。实测到的量级：应用心跳静默 2140 拍（1.07 s）、主循环单轮被拉长到 10.6 s（应为 5 s），并触发一次 `heartbeat` 三次连续故障判定、槽 0 被 hold（故障日志写在 `.noinit` 区，跨复位保留，下次开机还会复现）。插入排序改成与到期判定一致的有符号形式后重测：跨回绕的两条 `APP_ALIVE` 间隔精确 5.000 s，`fault` 无记录，`sched` 一致。

**不显式摘链**：任务被提前唤醒时，只做 `svcrt_delay_disarm()`；万一漏了，到期时节点还在链上，靠 `status != WAIT` 判定为僵尸直接丢弃。这条"宽容"设计把"漏摘链导致任务被误唤醒"这类难查问题换成了无害的空转，代价是链上可能短暂存在已被唤醒的节点。

**如实声明**：延时链的**插入仍是有序插入 O(N)**（与 RT-Thread 的 `rt_timer_start` 同复杂度），只有"每拍处理"降到了均摊 O(1)。任务数不大时这不是瓶颈，但它不是 O(1)。

### 2.4 状态同步点

就绪集是 `status` 的**索引**，不是真相。所有会改变"某任务是否可运行 / 优先级是多少"的地方都必须同步：

| 位置 | 动作 |
|------|------|
| `svcrt_cfg.c` 任务注册 | 链字段初始化 + `svcrt_ready_add()`；`svcrt_cfg_load()` 里 `svcrt_ready_reset()` |
| `svcrt_task.c` PendSV 激活 | 当前任务转 `RUNNING` 前先把旧任务改回 `READY`（仍在就绪集里） |
| `svcrt_task.c` 阻塞/延时 | `svcrt_ready_del()` + `svcrt_delay_arm()` |
| `svcrt_task.c` 栈溢出 / 故障下线 | `svcrt_ready_del()` + `svcrt_delay_disarm()` |
| `svcrt_sync.c` / `svcrt_mq.c` / `svcrt_event.c` / `svcrt_timer.c` | 唤醒后 `svcrt_ready_add()` |
| `svcrt_sync.c` 优先级继承提升/回退 | `svcrt_ready_reprio(idx, old_prio)`（`old_prio` 必须在改 `priority` **之前**取） |
| `svcrt_loader.c` 强制下线任务 | `svcrt_ready_del()` + `svcrt_delay_disarm()` |
| 节拍 | 时间片到点 `svcrt_ready_rotate()` |

漏一处的后果是"任务永远不被选中"或"已阻塞的任务还被选中"这类静默错误，**不会报错也不会崩**。所以本轮同时加了 §5 的一致性自检命令。

## 3. 三条兜底，专治"漏改一处"

### 3.1 `svcrt_ready_add/del/unlink` 全部幂等

`svcrt_ready_add()` 先看 `ready_next != NIL` 就返回（已在链上直接忽略）；`del` 对不在链上的任务无操作。这样"多调一次"是安全的，只有"少调一次"才会丢任务。

### 3.2 位图与链表由同一条路径维护

入桶/出桶只在 `svcrt_ready_link()` / `svcrt_ready_unlink()` 里改位图，别处不直接碰 `svcrt_ready_map`。位图与链表因此不会各自漂移。

### 3.3 首次调度前从 `status` 重建一次

```c
static uint8 svcrt_ready_built = 0u;      /* 首次调度前重建就绪集的一次性标记 */

int32 svcrt_sched_next(void)
{
    if(svcrt_ready_built == 0u) { svcrt_ready_rebuild(); svcrt_ready_built = 1u; }
    ...
}
```

`svcrt_ready_rebuild()` 清空所有桶与链字段，然后遍历任务表，把 `READY` / `RUNNING` 的任务重新挂进去。

**为什么需要**：示例工程的 `svcrt_register_tasks()` 是**手工填 TCB**（不走 `svcrt_task_register()`），只写 `status = SVCRT_TASK_READY`。旧调度器按 `status` 全表扫描，所以这种写法"能跑"；换成位图+链表后，这类任务就永远选不到了。这不是理论上可能，是这一轮**真机上撞到的**：`sched` 命令报 `INCONSISTENT, 3 mismatch(es)`，逐条打印显示两个 LED 任务 `status=READY` 但 `ready_next=ready_prev=255`（不在任何桶里），静默饥饿。

处置是双保险：内核侧用"首次调度前从真相重建索引"兜住**这一类**手工写法（O(N) 只发生一次，与调用顺序无关），示例侧同时补上 `base_priority` 与 `svcrt_ready_add()`（`base_priority` 缺了会让优先级继承回退时把任务提到优先级 0）。

## 4. 代价账

设任务数 `N`（≤ 48）、优先级值域 1..254。

| 操作 | 改动前 | 改动后 |
|------|--------|--------|
| 选下一个任务 | O(N) 全表扫描 | **O(1)**（两级位图 + 链表头） |
| 任务进入/离开就绪 | O(N)（无显式结构，靠扫描发现） | **O(1)**（链表插入/摘除 + 位图置/清位） |
| 优先级变更（继承提升/回退） | O(N) | **O(1)**（摘链 + 重挂） |
| 同优先级轮转 | O(N)（重扫一遍比 `touch_tick`） | **O(1)**（环形链队首转队尾） |
| 每拍倒计时 | O(N) 全表逐个减 | 均摊 **O(1)**（延时链只看到期链头） |
| 延时/周期任务入链 | O(N)（原来也是） | **仍是 O(N)**（有序插入，未改成时间轮） |
| 首次调度 | — | O(N) **一次**（§3.3 重建） |

RAM 代价：每个 TCB 多 `ready_next/prev`、`delay_next/prev`（各 1 字节）、`delay_tick`（4）、`slice_tick`（4）、`delay_queued`（1），48 个任务合计约 576 B，由 `SVCRT_TASK_TABLE_RAM_MAX` 的编译期断言把关。位图与链表头是文件级静态数组：`8×4 + 1 + 256 + 1 + 4 + 1` ≈ 290 B。

## 5. 验证

### 5.1 一致性自检命令

新增 shell 命令 `sched`：

```
sched: consistent (bitmap/links == task table)
```

它把两套东西对照：位图/链表所表达的"就绪集 + 各任务优先级"，与任务表 `status` / `priority` 所表达的真相。不一致时**逐条打印**差在哪（`#idx prio= status= on_ready= next= prev=`），而不是只报一个数字——只报数量等于给了把没钥匙的锁。

本轮实测：修复 §3.3 之前报 `INCONSISTENT, 3 mismatch(es)`（两个 LED 任务 + 计数），修复后连续两次查询均为 `consistent`，`ready=1 top=6`（当时只有内核任务在就绪集里，其余在周期等待）。

### 5.2 编译

- **AC6 语法检查**：`armclang -fsyntax-only`（`--target=arm-arm-none-eabi -mcpu=cortex-m4 -mfpu=fpv4-sp-d16 -mfloat-abi=hard -std=c99`）对 `kernelsrc/src` 全部 `.c` 与 `svcrt_shell.c` 通过，只剩 3 处既有的 VLA-folding warning。
- **Keil UV4 全量重建**（AC5 V5.06u7）：`0 Error(s), 1 Warning(s)`，唯一 warning 是基线的 `svcrt_context.S(134) A1581W`（对齐填充）。`Code=51326 RO-data=3710 RW-data=320 ZI-data=38896`（改动前 `Code=49030`，+2296 B）。
- **上板**：UV4 `-f` 烧录 F427，`Verify OK`，App/驱动镜像正常装载运行，`info` / `task` / `sched` 均正常。

### 5.3 上下文切换开销（F427 @96 MHz，3 秒窗口，DWT 周期计数）

读法：`pendsv` 行的窗口取自 `svcrt_trace_isr(14, ·)` 的进/出两点，夹住整趟 PendSV；`activate` 行取自 `svcrt_sched_activate()` 函数体（`SVCRT_SCHED_STAT_*`）。两组都读**窗口前后的差值**再算均值，不用开机以来的累计值（累计值里混着别的阶段）。

**先说口径**：板上 `svcrt_port_board_init()` 调 `svcrt_trace_init()`，**插桩默认是开的**（有意为之，为了能复现"复位到启动"那一段）。插桩开着时每趟切换自身要花约 1760 周期，量到的是插桩口径。要比调度器本身，必须先 `trace stop`。

| 配置 | PendSV 趟数 / 3 s | 往返均值 | activate 均值 | PendSV 占 CPU |
|------|------------------|---------|--------------|--------------|
| **插桩关**：全表扫描（`a9e7b80`） | 3129 | **710.5** | 83.6 | 0.768% |
| **插桩关**：位图 + 链（本轮） | 3129 | **430.9** | 99.5 | **0.448%** |
| 插桩开（默认固件口径）：全表扫描 | 3118 | 2480.8 | 958.0 | 2.67% |
| 插桩开（默认固件口径）：位图 + 链 | 3121 | 2194.1 | 965.5 | 2.37% |

读这张表要注意四点：

- **切换次数两边一样**（3129 vs 3129），所以均值可以直接比——这是本轮唯一一处"同工作量 A/B"，两组固件跑的是**同一批 App/驱动镜像**，只换了内核。
- **降的是调度决策那一段**。`activate` 本身不含查找，O(1) 不改它（83.6 → 99.5，绝对值 +16 周期，未做重复测量以区分是否有系统性差异）。真正的下降在 `710.5 − 83.6 = 627` → `430.9 − 99.5 = 331`，约 **−47%**；整趟 PendSV **−39%**。
- **插桩口径的下降幅度不一样**（2480.8 → 2194.1，只 −11.6%），因为大头被 1760 周期的插桩开销盖住了。**不要**拿插桩口径的数字去谈调度器优化了多少。
- **与开源 RTOS 对照要谨慎**：FreeRTOS Cortex-M4 公开口径的上下文切换在 200~300 周期量级，但那是"不带 MPU 区域重配、不带隔离检查"的路径。这里的窗口里含 `svcrt_mpu_set_app()`（App 间切换要重配 MPU 区域，架构必需）与 `svcrt_trace_isr` 两次钩子调用。要拿到可比数字，需要在同一块板上跑对方的移植版本，**这一步没做**。

浮点上下文不在这个窗口里单独计量：本内核用惰性保存（`FPU_FPCCR_ASPEN`），只有真正用到 VFP 的任务才会多压栈，报告里没有把它拆出来。

## 6. 还没做的优化空间

如实列出，未做的不写成已做：

1. **延时链插入仍是 O(N)**：改成时间轮（timer wheel）或按桶分组的到期队列可以把插入也压到 O(1)。取舍与就绪集相同——多一份结构就要多一组同步点，而本轮已经因为"索引与真相脱钩"踩过一次（§3.3），加结构要配自检。
2. **时间片轮转未做专门的压测**：代码路径（`slice_tick` 递减 → `svcrt_ready_rotate` → 环形链队首转队尾）已编译、已上板连续运行，但**没有**构造"两个同优先级 CPU 密集任务"来实测轮转是否按 5 ms 交替。现有 App/驱动镜像里的任务都是周期等待型，不构成这个场景。
3. **同优先级轮转不再依赖 `touch_tick`**：`touch_tick` 字段仍在、仍在更新（栈用量与诊断用），但已不参与调度裁决——现在由环形链的队首决定。§1 表格里旧文档提到的"比 `touch_tick` 取更早者"已不成立。
4. **调度延迟/抖动仍未测**：本轮量的是"切换一次要多少周期"，还不是"从中断发生到任务真正运行"的最坏延迟。后者要在 trace 上打点，`mdkdebug` 的 buff 后端能到每 CPU 周期粒度。
5. **插桩默认开启的固定开销**：见 §5.3——不给主机读数时，插桩仍每趟花约 1760 周期（≈1.9% CPU @ 1 kHz 切换率），且因为没人搬运而持续丢事件（实测 `trace` 命令报 `138068 events were dropped`）。这是设计取舍（要能复现启动段），但如果只关心稳态性能，"上电默认关、需要时 `trace start`"更划算。**没改**，因为改的是默认行为。
6. **`sched` 自检是手动命令**：只能靠人敲。理想做法是让它能在断言失败时主动记录一次快照（或提供一个廉价的自检计数器），现在没有。
