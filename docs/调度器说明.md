# 调度器说明

调度器是内核里唯一一个**每个节拍都要跑、每次阻塞/唤醒/抢占也都要跑**的模块。本文说明它的模型、这一轮做的两项瘦身、等价性依据，以及还没做的部分。

源码：`kernelsrc/src/svcrt_task.c`（调度主体与节拍处理）、`kernelsrc/src/svcrt_cfg.c`（任务注册）。

---

## 1. 模型

| 项 | 取值 / 语义 |
|----|------|
| 策略 | **优先级抢占** + 同优先级**时间片轮转** |
| 优先级 | `1..254`，**数值越小越紧急**。`255` 是"无候选"哨兵，不是合法优先级，创建时显式拒绝而不是静默钳制 |
| 任务上限 | `SVCRT_TASK_MAX_NUM = 48`（静态 TCB 数组），其中内核自带与示例静态任务预留 `SVCRT_TASK_MAX_KERNEL = 8` |
| 节拍 | `SVCRT_TICK_PERIOD_US = 500`（2 kHz）。所有超时以毫秒对外，内部按节拍折算 |
| 任务状态 | `INVALID` / `READY` / `RUNNING` / `WAIT` |
| 候选集 | `READY` 与 `RUNNING` 都算"可运行"——正在跑的任务本身也要参与比较，否则它会在自己身上"输掉"选择 |
| 同优先级裁决 | 比 `touch_tick`，取**更早**的那个。`touch_tick` 在任务被选中/激活时更新，从而形成轮转 |
| 所有任务都不可运行时 | 返回 `-1`，由调用方走 idle |

任务切换点：`SVCRT_SWITCH_TASK()`（PendSV）。调度决策由 `svcrt_sched_next()` 给出。

---

## 2. 这一轮改了什么（P4b）

改动只有两处，都是"把工作从高频路径搬到低频路径"，没有改语义。

### 2.1 倒计时扫描：从"每次调度决策"搬到"每节拍一次"

**原先**：`svcrt_sched_next()` 里先遍历全表，对每个任务调一次 `svcrt_tick_tasks()` 做倒计时。而 `svcrt_sched_next()` 是**每次调度决策**都会走的路（不仅仅是节拍），于是任务表被反复扫了很多遍，而倒计时其实只由节拍推进。

**现在**：扫描搬到 `svcrt_sched_tick_sweep()`，由 `svcrt_kernel_tick_handler()` 每拍调用一次；`svcrt_sched_next()` 只做选择。

```c
void svcrt_kernel_tick_handler(void)
{
    svcrt_kernel_tick++;
    ... cpu 负载采样 ...
    svcrt_timer_tick_handler();     /* 软定时器倒计时 */
    svcrt_sched_tick_sweep();       /* 任务倒计时扫描 + 重建优先级缓存 */
    SVCRT_SWITCH_TASK();
    ...
}
```

**为什么位置等价**：`escape_tick` 是"距上次处理过去了几个节拍"，只有节拍在推进它，所以一拍处理一次不会漏。原先扫描发生在 `svcrt_timer_tick_handler()` 之后（`sched_next` 由 PendSV 触发），现在紧接其后、任务切换之前，因此**本拍被超时唤醒的任务在当拍就能被选中**——与原行为一致。

### 2.2 选择路径：加一条 O(1) 快速路径

缓存三个量（`svcrt_pri_cache_*`）：所有非 `INVALID` 任务里**最小的基准优先级** `pri_min1`、**次小的** `pri_min2`、以及取到最小值的任务个数 `pri_min1_cnt`。

`svcrt_sched_next()` 先试快速路径：

```c
if(缓存有效 && 当前任务存在)
{
    other_min = pri_min1;
    if(当前任务的 base_priority == pri_min1 && pri_min1_cnt == 1)
        other_min = pri_min2;          /* 当前任务就是唯一最小者，取次小 */

    if(当前任务 READY 或 RUNNING && 当前任务 priority < other_min)
        return 当前任务;                /* 没人能抢它，不必扫表 */
}
... 原全表扫描 ...
```

**等价性论证**（这是这次改动的核心，不是"看起来没问题"）：

- 比较用**有效优先级** `priority`（会被优先级继承压低数值），缓存存的是**基准优先级** `base_priority`（只在创建/下线时变化）。
- **优先级继承只会让别的任务数值变小（更紧急），不会让它们变大。**
- 因此"当前任务的有效优先级**严格小于**其余所有任务的基准优先级"就蕴含"当前任务的有效优先级小于其余所有任务的有效优先级"——没有任何任务能抢在它前面，直接返回它是正确选择。
- 条件不成立时**原样退回全表扫描**，结果与改动前完全一致。

注意两个细节：条件用**严格小于**（相等时要靠 `touch_tick` 轮转，必须走全表）；当前任务若正好是唯一最小者，要拿 `pri_min2` 比，否则会拿自己跟自己比而永远判为"不严格小于"（保守但白丢快速路径）。

## 3. 缓存的生命周期

| 时机 | 动作 | 理由 |
|------|------|------|
| 任务注册（`svcrt_cfg.c`） | `svcrt_sched_pri_cache_drop()` 立即作废 | 新任务的基准优先级可能更紧急，缓存必须立刻失效，否则快速路径可能错误地留下当前任务 |
| 每节拍 | `svcrt_sched_pri_cache_rebuild()` 重建 | 让缓存定期自愈，不依赖每个改动点都记得作废 |
| 任务下线 | 不显式作废 | 已消失任务留在缓存里会让**别的**任务显得更紧急（`other_min` 偏小），快速路径条件更难成立，只是退化成全表扫描——**偏低是保守方向，不会给出错答案**；下一拍重建即修正 |

设计取向很清楚：**允许保守退化，不允许乐观出错。** 会朝"更激进"方向漂移的那一类改动（新建任务）必须是显式作废；朝"更保守"方向漂移的那一类（删除任务）交给周期性重建兜底即可。

## 4. 代价账

设任务数 `N`（≤ 48）。

| | 改动前 | 改动后 |
|--|--------|--------|
| 每次调度决策 | O(N) 全表扫描 + 每项一次 `svcrt_tick_tasks()` | 命中快速路径时 O(1)；未命中退化为 O(N) |
| 每节拍 | （含在调度决策里，同一次） | O(N) 一次（倒计时 + 缓存重建） |
| 最坏情况 | 不变 | 不变（快速路径失效即回到原路径） |

也就是说：**最坏情形没有变差，常见情形变好**。常见情形是"当前任务一直是最高优先级"——此时每次被唤醒/抢占/节拍都走 O(1)，不再扫表。典型场景（一个 App 线程 + 内核任务 + idle，最高优先级任务长期就绪）就落在快速路径上。

## 5. 验证

- **编译**：F427 / F401 内核均 0 Error（F427 `Code=47958`，F401 `Code=46526`）。
- **行为等价**：真机上 APP_DEMO 十段自测（含 POSIX/Windows 段）全部通过；心跳任务 `APP_ALIVE` 持续输出（`t=6364ms / 11366ms / 16367ms`，`cpu=0%`，`timer_hits=3`），说明周期任务、阻塞唤醒、超时路径都在正常工作。
- **异常路径**：`app stop` / `app start` 反复启停后调度仍正常（任务槽位回收后被重新使用）。

这些是"行为一致"的证据，不是形式化证明。§2.2 的论证属于推理层面，两者互补。

## 6. 还没做的优化空间

如实列出，未做的不写成已做：

1. **就绪表仍是全表扫描**：快速路径未命中时（例如多个同优先级任务轮转、或当前任务不是最高优先级）要扫 48 项。教科书 RTOS（FreeRTOS 的 `uxTopReadyPriority` + `pxReadyTasksLists[]`、Zephyr 的 run queue）用优先级位图把这一步压到 O(1)：优先级 1..254 需要 8 个 32 位字，查最低非零字用 CLZ 指令，一拍就能定出最高就绪优先级。
   **没做的原因**：位图要求**每一个**改 `priority` 或 `status` 的位置都同步维护位图（创建、下线、优先级继承提升、继承回退、超时唤醒、主动阻塞……），漏一处的后果是"任务永远不被选中"这类难查问题。当前的任务集合（≤48，且实际常见 5 个左右）下，全表扫描的收益不足以抵这个风险。要做就单独一批，配套一个"位图与任务表一致性自检"的调试命令。

2. **每拍 O(N) 的倒计时扫描**：延时/周期任务通常只占少数。可以改成按到期时间排序的链表或时间轮，让每拍只处理到期的那些。同样的取舍：多一份数据结构要与状态变更保持同步。

3. **快速路径的覆盖度**：`other_min` 用的是全体的最小基准优先级。若当前任务不是最高优先级，快速路径不命中而扫全表——这是必须的（得找出更高的那个）。可以再加一条"次高候选缓存"，但复杂度上升、收益有限。

4. **同优先级轮转的 `touch_tick`**：靠单调增长的时间戳比较，没有做溢出处理，也没有对应的测试用例。按 0.5 ms 节拍折算，`uint32` 一轮约 24.8 天，长时间连续运行的设备会经过这个边界，届时的轮转顺序需要实测确认，而不是假定它没事。

5. **没有调度延迟/抖动测量**：现在只有 CPU 负载统计（`svcrt_kernel_get_cpu_busy_ticks`）。要做定量对比（如中断到任务运行的最坏延迟），得先在 trace 上打点——`mdkdebug` 的 buff 后端已经能做到每 CPU 周期的粒度，这是后续可用的手段。
