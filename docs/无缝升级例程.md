# 无缝升级例程：运行中升级控制回路

本篇讲 `example/stm32f427/app_sdk/SEAMLESS_V1` 与 `SEAMLESS_V2` 这对小程序例程：
一个控制回路以**小程序**形态活在 RAM 里，新版本作为一个新文件被写进**外部 NOR 卷**，
写完后新版本接管同一个受控量。整个过程里控制回路不被冻结，新程序接着旧程序的状态继续跑。

**结论分档**（见 `skills/svcrtos/SKILL.md` §6 的三档口径）：

| 结论 | 档位 |
|------|------|
| 两个版本各自编译、打包、镜像自检通过 | 编译通过 |
| 上板：V1 稳态运行、V2 写进卷、V2 接管、迭代数与受控量跨版本连续 | **上板验证过** |
| 反例：旧版抢不回控制权、无人释放时新版退出、新版放弃时撤回请求 | **上板验证过** |
| 失败回滚 / 版本自动发现 / 装载停顿消除 | **未做**（见 §8） |

内核**一行未改**——本示例只用了既有的小程序装载、SVC 门面（文件、控制台、任务、心跳）与
文件系统。文章里所有数字都来自设备自己在控制台打印的遥测，没有主机侧计时。

## 1. 为什么是「小程序 + 外部 NOR」

要在运行中换掉正在跑的控制逻辑，最直觉的做法是片内 Flash 做 A/B 双区。这条路在本板上走不通：
`sched_lock` 之下的片内擦除会让取指停住约一秒，
`kernelsrc/src/svcrt_installer.c` 里就写着这件事（"an erase mid-frame stalls the CPU for about a second,
the RX interrupt cannot run"）。片外 NOR 没有这个问题：擦写只阻塞**发起写的那个任务**，
不冻结 CPU；代价是写完要有人重新读进来执行——这正好是小程序的用法：

- 小程序**不安装、不占固定槽位**，从文件系统读进 RAM 执行，退出即归还两块内存；
- 新版本只是卷里的一个新文件，写它不动片内 Flash；
- 装载是唯一一次「内核把调度锁拿在手里」的动作，实测时长见 §5。

## 2. 目录与产物

| 路径 | 内容 |
|------|------|
| `example/stm32f427/app_sdk/SEAMLESS_V1/` | 1.0.0，周期 10 ms，被接管的那个；`Src/seamless_v1.c` + `Src/seamless_proto.h` |
| `example/stm32f427/app_sdk/SEAMLESS_V2/` | 1.1.0，周期 5 ms，接管的那一个；`Src/seamless_v2.c` + `Src/seamless_proto.h` |
| `build/seamless_v1.svcapp` / `build/seamless_v2.svcapp` | `type = miniapp`、`flags = 不自启` 的镜像（构建产物，未入库） |

两个工程的 `seamless_proto.h` **逐字节相同**，是刻意重复：它是两个版本之间的接口，
任何一侧都不能单独改。改的规矩只有一句——同一提交改两份，并把记录 magic 尾字符一起加一，
这样新版本永远不会把旧版本留下的记录当成自己的。

## 3. 交接协议：卷上的两条记录

文件写不是原子操作，读者可能正好读到写了一半的记录，所以两条记录都是**定长 + magic + CRC32**
（位式实现，不查表），读者先校验再使用。

`/sx_state.bin`（64 B，写者 = 当前控制者，平态**不写**）：

| 偏移 | 字段 | 说明 |
|------|------|------|
| 0 | magic | `SXS1`（`0x31535853`） |
| 4 | crc | 覆盖 8..63 |
| 8 | seq | 每次写 +1 |
| 12 | owner | 版本身份：1 = V1（1.0.0），2 = V2（1.1.0） |
| 16 | phase | 1 = ACTIVE 控制中，3 = RELEASED 已交权 |
| 20 | tick_ms | 最近一次控制迭代的墙上时间 |
| 24 | iterations | 累计迭代数 |
| 28..40 | setpoint / pv / integ / out | 控制器与受控量，千分之一定点 |
| 44 | gap_max_ms | 迄今最大迭代间隔 |
| 48 | overruns | 间隔 > 2×周期 的迭代数 |
| 52 | period_ms | 写者的控制周期 |
| 56,60 | reserved | 0 |

`/sx_req.bin`（32 B，写者 = 新版本）：

| 偏移 | 字段 | 说明 |
|------|------|------|
| 0 | magic | `SXR1`（`0x31525853`） |
| 4 | crc | 覆盖 8..31 |
| 8 | from_version | 请求方看到的在位版本 |
| 12 | to_version | 请求方自己的版本 |
| 16 | cmd | 1 = HANDOVER |
| 20 | req_tick_ms | 写请求的时刻 |
| 24,28 | reserved | 0 |

两条记录都带**写者身份**，这决定了两条硬规则：

- 只有当前控制者写 `/sx_state.bin`，它写完 `RELEASED` 之后不再碰任何东西；
- 只有请求方写 `/sx_req.bin`，**也由它自己撤回**（放弃接管时要撤，见 §7）；
- 供方只认 `to_version > 自己版本` 的请求，别人的请求——包括失败接管留下的残根——不是它的。

## 4. 交接时序

```
V1 稳态 ──每 100 ms 读一次 /sx_req.bin（无请求 = 安静）
主机  ── fs put 把 V2 写进卷（只写 NOR，不动片内 Flash）
主机  ── mini run V2  ← 唯一的装载停顿
V2    ── 读状态 → 写 /sx_req.bin → 每 50 ms 轮询状态等 RELEASED（上限 5000 ms）
V1    ── 读到请求 → 打印 → 写一次 RELEASED 状态 → 删 /sx_req.bin → 返回（内核归还两块内存）
V2    ── 看到 RELEASED → 接管 → 打印 handover_gap → 写 ACTIVE → 进入自己的循环
```

状态行里 `gap=` 是**迄今最大迭代间隔**，`over=` 是间隔超过 2×周期的迭代数，`pr=` 是**轮询这次
文件读**的最长耗时；V2 多一列 `last=`（刚过去那一轮的间隔）。V1 打印 `[v1] v=1.0.0`，
V2 打印 `[v2] v=1.1.0`——版本、周期、列数三处都能看出是谁在控制。

## 5. 实测数据（F427，115200，设备侧遥测）

**V1 单独跑（基线）**：93 iterations/s ⇒ 实际周期 **10.7 ms**（标称 10 ms），
`gap=17`（就是「10 ms 等待 + 7 ms 轮询读」那一轮），`over=0`，`pr=7 ms`。

**写新镜像进卷（`fs put` 6116 B，不启动任何小程序）**：

| 指标 | 实测 |
|------|------|
| 循环最大空洞 | 没有超过 193 ms（沿用上一相位的记录，本相位未刷新） |
| 迭代速率 | ~90 /s（空闲 93.5 /s） |
| 轮询读耗时 | 明显变长：本窗口内每次轮询的间隔都越过 2×周期 的线（`over` 以 ~10/s 增长） |

也就是说：写卷**没有**把循环停住，但它会把循环里那次文件读拖长——读要排队等上传者手里的文件系统。

**装载另一个小程序（镜像已在卷上，只装载不写卷）**：

| 指标 | 实测 |
|------|------|
| 循环最大空洞 | **193 ms** |
| 那一秒的迭代数 | 34（空闲 93）⇒ 整秒丢约 0.5 s 循环时间 |
| 轮询读耗时 | 最长 **100 ms** |

**交接（同一套脚本四次运行）**：

| 指标 | 实测 |
|------|------|
| 请求写入 → 供方察觉 | 109 ~ 213 ms |
| `handover_gap_ms`（供方 `tick_ms` → 新版确认） | **27 / 31 / 224 / 407 ms** |
| 其中「发布一次状态」的耗时 | 常规 8 ~ 19 ms，有一次 **218 ms** |
| 迭代数连续性 | `it=994` → 接管后 `resumed at it=994`（逐字连续，无回零） |
| 受控量连续性 | 接管时 `pv=44.249 / 46.413 / 51.692`，未从 0 重启 |
| V2 周期 | 166 ~ 168 iterations/s ⇒ **5.9 ms**（标称 5 ms） |
| `guard` | `verdict=0x0`、`starves=0`；`fault` 行数交接前后不变（优雅退出不记 fault） |

交接窗口里的最坏情况是 407 ms，判据要求 < 1000 ms，全部通过。407 ms 那一跑里发布耗时没有被仪器
覆盖；同一条 64 B 记录在别的运行里量到过 218 ms，所以**主导项是发布这次 littlefs 提交**，
剩下的是两侧的轮询间隔（供方 100 ms、新版 50 ms）。

## 6. 判据与复现

判据（脚本自动判定，全部通过）：

1. 上传期间供方仍在按秒发布状态行（上传窗口里抓到 `[v1] v=…`）；
2. 供方打印「收到请求」「已发布并释放」两条；
3. 新版打印一次「接管」，且 `handover_gap < 1000 ms`；
4. 迭代数跨版本连续、受控量不回零；
5. `gap_max < 1000 ms`（两侧各自记录）；
6. 交接前后 `fault` 行数不变；`guard starves=0`。

复现：

```bash
# 打包（两个工程各一次）
py -3 tools/pack_app.py --project example/stm32f427/app_sdk/SEAMLESS_V1/MDK-ARM/seamless_v1.uvprojx \
        --type miniapp --no-autostart --out build/seamless_v1.svcapp
py -3 tools/pack_app.py --project example/stm32f427/app_sdk/SEAMLESS_V2/MDK-ARM/seamless_v2.uvprojx \
        --type miniapp --no-autostart --out build/seamless_v2.svcapp

# 上板（设备侧，串口 115200；`mini run` 的路径用卷内绝对路径）
fs rm /sx_state.bin                       # 清掉上一跑的现场（可选）
fs put /seamless_v1.svcm 5088             # 用 tools/fs_put.py 送
mini run /seamless_v1.svcm                # V1 接管，每秒一行状态
fs put /seamless_v2.svcm 6116             # 运行中把新版本写进卷
mini run /seamless_v2.svcm                # 新版请求、接管
```

## 7. 上板暴露并修掉的两处

**一、轮询间隔不能等于循环周期。** 第一版把轮询间隔设成 20 ms（周期 10 ms），实测周期变成
**23 ms**、`over` 每次迭代都计数。原因不是调度，是那次文件读：一次 32 B 记录的
littlefs open/read/close + SPI NOR 大约 **7 ~ 15 ms**，把它放在每个周期里，循环就只能按文件系统的
速度跑。改成 10× 周期（V1 100 ms、V2 50 ms）后循环回到 10.7 ms / 5.9 ms。

**二、放弃接管时必须撤回自己的请求。** 反例测试（状态记录写着「owner 1 在控制」而实际没有人
在跑）时新版会超时退出——但卷上留下了一个 `to_version = 1.1.0` 的请求。供方只按 `cmd == HANDOVER`
判断，于是它会照着这个残根把循环交出去，而请求方早已退出：**结果是没人控制**，比一次失败的升级
更糟。两处一起修：

- 新版放弃前删掉自己写的 `/sx_req.bin`（谁写谁撤）；
- 供方只认 `to_version` 比自己新的请求（`seamless_v1.c` 的 `request_pending()`）。

## 8. 边界与未做项

- **装载停顿没有消除**，只是被测出来：装载 5.4 KB 小程序的那一跑里循环最大空洞实测 416 ms
  （同一次运行里也含上传，未单独分离；单独测上传没有超过 193 ms）。这一项按约定「不改内核，
  如实测量并报告」。
- **不做失败回滚 / 版本退化**：接管失败时新版本退出、旧版本继续控制，这是刻意的一致性优先。
- **不做版本自动发现**：新版本由主机 `mini run` 显式启动，没有「扫描卷并自行升级」的逻辑。
- **小程序没有「停另一个小程序」的 API**，所以交接通道走卷内文件，而不是进程间通知。
- **`fault` 里的 `TASKKILL` 行**：人工 `mini stop` 会在 loader 侧记一条（把任务踢出调度的记账）。
  优雅退出不记；本次验收正是用「交接前后 fault 行数不变」来证明这一点的。
- **`[v2] asking version 1.0.0 (owner 1, it=0)` 里的 `it=0` 不是 bug**：供方稳态不写文件，
  卷上那条 ACTIVE 记录还是它启动时写的快照，迭代数只在交接那一刻才被刷新。
