# 崩溃恢复与镜像版本把关

这份文档覆盖两件事，它们都回答"设备上出了事之后会怎样"：

- **B 项**：一个镜像反复崩溃，内核怎么不再让它把整机拖进重启环；
- **C 项**：一个镜像要被装进池子之前，内核怎么判断"该不该装"。

以及一件**明确不做**的事：签名验签与升级/回滚（见 §5）。

---

## 1. B 项：崩溃终局与跨复位计数

### 1.1 计数存在哪

崩溃计数有**两份**，用途不同：

| 位置 | 生命周期 | 用途 |
|---|---|---|
| 共享 RAM 里的 `slot_crash_cnt` | 本次上电 | 运行期查询（`app` 列表的崩溃数列） |
| 共享 RAM **尾部 UNINIT 区**的 `svcrt_crash_journal_t` | **活过复位，掉电才清零** | 跨复位累计，挡住"崩溃→复位→再崩溃"的启动环 |

日记落在 `config/svcrt_partition.h` 定义的区域里：

```c
#define CRASH_LOG_SIZE  (512)
#define CRASH_LOG_BASE  (SHARE_RAM_BASE + SHARE_RAM_SIZE - CRASH_LOG_SIZE)
```

结构体大小在编译期对着 `CRASH_LOG_SIZE` 做静态检查——**加字段加不出空间是编译错误**，
不会静默覆盖共享 RAM 尾部的别的数据。

### 1.2 日记字段

| 字段 | 含义 |
|---|---|
| `magic` | `SVCRT_CRASH_MAGIC = 0x5343524A` |
| `version` | `SVCRT_CRASH_VERSION = 1` |
| `seq` | 每次提交写入自增 |
| `boots` | 记在这里的启动次数；`>= 2` 说明上一回的内容真的活过了一次复位 |
| `crash_cnt[]` | 每槽连续故障数 |
| `last_reason[]` | 最近一次故障的原因 |
| `dis_reason[]` | 该槽为什么被禁用（0 = 未禁用） |
| `dis_tick[]` | 禁用时刻的 tick（0 = 本次上电之前） |
| `base[]` | 该条目对应的池地址 |
| `check` | 覆盖以上全部字段的校验和 |

### 1.3 三条不猜的规则

1. **magic / version / checksum 任一不过，整本日记作废重开**，而不是"试着信一半"。
   残留 RAM 字节和写了一半的记录看起来都像数据，照着行动就会把一个镜像
   因为它从没做过的事禁用掉。
2. **只对"镜像还停在当初那个地址"的槽位采用计数**。空槽、被换掉的镜像、被搬走的镜像，
   条目一律丢弃——把陈旧计数记到新来者头上，就是拿别人的错罚它。
3. **禁用理由分三种，不混为一谈**：
   `SVCRT_CRASH_REASON_FAULT(1)` 连续故障到上限 /
   `SVCRT_CRASH_REASON_HEARTBEAT(2)` 违反自己声明的心跳契约 /
   `SVCRT_CRASH_REASON_AUDIT(3)` 运行期结构自审失败。

### 1.4 上限是多少

`config/svcrt_partition.h`：

```c
#define APP_CRASH_RESTART_MAX 3    /* 连续故障重启上限：达到后禁用该 App 槽位（0=不限次自动重启）*/
```

布局配置里可以用 `fault_restart_max`（1..64）按布局覆盖，`0` 表示沿用上面的编译期值。
**重新安装镜像时计数清零。**

到上限之后：槽位置为 `INVALID`，任务脱离调度，并且**不再自启**。
人工重启用 `svcrt_loader_start_manual()`（控制台 `app start <slot>` 走的就是它）——
禁用的语义是"除非有人明确要求，否则别再自己跑起来"。

### 1.5 心跳是应用自己的合同，不是内核的猜测

`svcrt_heartbeat(period_ms)` 让镜像声明"我最久隔这么久报一次到"。

- 周期下限 `SVCRT_GUARD_MIN_PERIOD_MS = 100` ms（等于服务采样周期）。
  比采样间隔还短的窗口判断不了，内核**拒绝**而不是看着一组它验证不了的数字下结论。
- 从没声明过周期的镜像，`guard` 报的是 **"未声明"**，不是"健康"——内核没有判健康的基础，就不给判语。
- 判定只看**报到的间隔**，不看任务当时在干什么。所以"睡/阻塞比声明周期还久"就是违约：
  周期是镜像自己的承诺，就得覆盖镜像自己最长的那次等待。豁免阻塞任务会让
  "睡→干活→报到"这种最常见形态失去约束，永远醒不来的镜像反而抓不到。
- 合同随任务结束而结束：任务被删的条目直接丢掉，不会留到 id 复用、记到另一个镜像头上。
- 内核自己收集的证据（每次 SVC 调用、在节拍上正在跑）**单独成列**，不折进合同——
  折进去就会 silently 放过一个卡死但恰好还在 CPU 上的镜像。

### 1.6 `crash` 命令

```
journal: 0x2000BE00 +512 bytes (uninitialized RAM: kept across reset, cleared by power-on)
boots=35 seq=100

slot type  faults last        hold      held_at
 1   app    3      fault       fault     12840
 2   drv    3      fault       fault     12840
 3   app    3      fault       fault     12840
```

（以上为 2026-09-22 F427 实测值：三个演示槽都撞到了上限被保持禁用。）

## 2. C 项：装进池子之前的版本把关

### 2.1 三态判定

`svcrt_loader_check_install()` 只按 **`image_id`** 比对（`image_id` = 负载的 crc32，
是负载身份；同一个应用两次打包只有版本号不同、`image_id` 相同）：

| 情形 | 结果 |
|---|---|
| 池内没有同 `image_id` 的有效副本 | 放行 |
| 同 `image_id`，且 `image_size` / `crc32` 也相同 | `SVCRT_LOADER_ERR_DUP(-17)` 重复副本 |
| 同 `image_id`，版本号不高于已装版本（降级回灌、同版本重建） | `SVCRT_LOADER_ERR_VERSION(-16)` 版本回灌 |
| 该槽位正处于 `LOADED` / `RUNNING` | 拒绝（先 `app stop <slot>`） |

设备侧原文：

```
[E][INSTALL] refused: version not increasing (id 0x%08X, incoming v%u.%u.%u.%u <= installed) - bump the version
[E][INSTALL] refused: identical image already installed (id 0x%08X, v%u.%u.%u.%u, %u B) - nothing to do
```

版本号是 4 段式，按大端排在 `version` 一个字里（`v[31:24].[23:16].[15:8].[7:0]`）。

### 2.2 断电恢复为什么不需要日志扇区

提交状态只有一个字段 `state`：搬移时先在新落点写一份 `UNCOMMITTED` 副本，
校验通过后**只把这一个字段**改写成 `VALID`（单字编程，原子），最后才擦旧副本。
上电扫描见到 `UNCOMMITTED` 一律丢弃；同 `image_id` 的两份 `VALID` 保留地址较低的那份。
两条规则合起来，恢复既是幂等的又是确定的。

> `state` **不能**拿来表达"卸载"：镜像提交后它已经是 0，写 `UNCOMMITTED`(=1) 要求把 0 置 1，
> Flash 做不到，硬件会静默保持 0，卸载于是变成空操作、镜像下次上电又回来。
> 卸载走的是清 `type` 字段（`SVCRT_APP_OFF_TYPE`），详见
> 《内核Shell控制台使用说明.md》"卸载的语义与空间回收的粒度"。

## 3. 排障入口

| 想知道 | 敲 |
|---|---|
| 跨复位崩溃账本、哪些槽被禁用、为什么 | `crash` |
| 心跳合同是否被违反 | `guard` |
| 结构自审是否通过 | `audit` |
| 故障环形记录（含 `INSTALLFAIL`） | `fault` |
| 某个任务卡在哪 | `task <id> <任意第三参>` |
| 安装为什么被拒 | `fault` + `log`（设备侧 `INSTALL` / `LOADER` 日志行） |

## 4. 结论分档

| 内容 | 档位 |
|---|---|
| 跨复位崩溃计数、上限禁用、`crash` 输出 | **上板验证过**（2026-09-22，F427：`boots=35 seq=100`，槽 1/2/3 撞上限被保持禁用） |
| `ERR_DUP` / `ERR_VERSION` 三态判定的代码路径 | **仅编译通过**（F427 / F401 / APP_DEMO / BLED_DRV 均 0 Error）；真机上未构造过重复副本与版本回灌两种输入 |
| 心跳违约导致禁用（`REASON_HEARTBEAT`） | **未验证**（未在板上构造过违约镜像） |
| 结构自审失败导致禁用（`REASON_AUDIT`） | **未验证** |

## 5. 明确不做的事（以及为什么）

| 不做 | 现状 | 原因 |
|---|---|---|
| **签名验签** | 镜像头有 `signature[64]`，**全 0，内核不读，主机端 `pack_app.py` 也写死 64 个 0** | 先只做完整性（CRC32）+ 版本单调 + 镜像身份。该字段的作用只是把偏移钉住，免得以后加验签时改动整个头的布局 |
| **A/B 双槽 / 自动回滚** | 没有 A/B 双槽，没有备份区 | 暂不做。但「运行中换掉控制程序」已有例程走通：控制回路以小程形态驻 RAM、镜像放外部 NOR，新版接管后接着旧版的状态跑，实测交接耗时 27 ~ 407 ms（`无缝升级例程.md`）——它做的是**交接**，不是回滚 |
| **持久化版本日志** | 只有 `.noinit` 区那本崩溃日记 | 版本日志不做，崩溃计数只在内存里记一下 |

> 因此：**`signature` 字段的存在不构成任何防篡改能力，不要把它当成"已签名"的证据。**
> 镜像头的注释里也是这么写的。
