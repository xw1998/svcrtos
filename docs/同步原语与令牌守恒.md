# 同步原语与令牌守恒

> 这份文档讲一件事：**SVCrtOS 里一个同步令牌（信号量计数、互斥锁所有权、条件变量的一次唤醒）
> 为什么必须、以及如何保证始终只有一个属主。** 前面先给结论，再给机制，最后给排障入口。

适用版本：`svcrtos_new` master，F427 / F401 双板。
文中标注的验证档位只有三档：**仅编译通过 / 上板验证过 / 未验证**。

---

## 1. 一句话结论

内核**不能在 SVC 处理器内部完成一次阻塞等待**，因为 `PendSV` 永远不能抢占 `SVC`
（`kernelsrc/port/arm/cortex-m4/svcrt_port.c` 的 `svcrt_port_switch_task()` 只做
`SCB->ICSR = SCB_ICSR_PENDSVSET_Msk`，注释写明了这一点）。因此从 App 发起的等待被拆成两半：

| 谁 | 做什么 |
|---|---|
| 内核（SVC 处理器内） | **只登记**：把等待者挂到对象的等待队列，然后返回 `SVCRT_SYNC_ERR_WOULDBLOCK` |
| App 侧 oslib（Thread 态） | **轮询 + 让出**：每 1 ms 问一次，问不到就 `svcrt_task_wait(1)` 睡一会儿 |

**令牌守恒就落在这条分界上**：派发方（post / unlock / signal / broadcast）看到队首是用户态等待者时
**不弹队列**，改为把令牌记进对象自己的 `count`，等下一次轮询从快路拿走。
于是任何时刻令牌只有两种状态——躺在 `count` 里，或者已经交给一个具体的就绪任务——不存在第三种。

---

## 2. 三条契约（改这块代码前必读）

### 契约一：用户态等待者只登记，真正让出发生在用户态

- 内核侧判据是 `svcrt_sync_in_handler()`，它委托 `svcrt_port_in_isr()`（读 `IPSR`）——
  全工程只有一处读 IPSR，别在别处再写一份。
- 处于 handler 态的等待调用返回 `SVCRT_SYNC_ERR_WOULDBLOCK(-4)`，
  调用方**必须**把它识别成"已登记，去轮询"，不能当成错误。
- oslib 的轮询粒度是 `SVCRT_APP_POLL_MS = 1` ms，轮询体是 `svcrt_task_wait()`。

### 契约二：派发方用 `peek(only_kernel=1)` 跳过用户态等待者

`svcrt_waiters_peek(waiters, only_kernel)` 是"看不弹"的查看函数。`only_kernel=1` 时，
带 appq 标记的等待者被跳过，于是：

- 派发方要么把令牌交给一个**能被就地恢复**的内核态任务（`wake_reason |= SVCRT_WAKE_HANDOFF`），
- 要么把令牌记进 `count`，等用户态等待者下一次轮询从快路取走。

直接 `pop` 一个用户态等待者等于把令牌交给一个没人服务的任务——那是泄漏，不是派发。

### 契约三：一个令牌只有一个属主

`count` 里有一个，或某个就绪任务手里有一个。两者不会同时成立。
违反这条契约的表现是"信号量明明 post 过、等待方却永远拿不到"，或反过来"两个任务同时认为拿到了锁"。

## 3. 返回值与唤醒原因

### 3.1 错误码（都是负值，0 = 成功）

| 名称 | 值 | 含义 |
|---|---|---|
| `SVCRT_SYNC_OK` | 0 | 成功 |
| `SVCRT_SYNC_ERR_PARAM` | -1 | 参数非法（句柄不在本类型区间、越界等） |
| `SVCRT_SYNC_ERR_TIMEOUT` | -2 | 等待超时 |
| `SVCRT_SYNC_ERR_DELETED` | -3 | 等待期间对象被删除 |
| `SVCRT_SYNC_ERR_WOULDBLOCK` | -4 | **已登记，尚未拿到**——不是错误 |

`WOULDBLOCK` 在 `svcrt_def.h:49` 与 `svcrt.h:37` 各有一份定义，都带 `#ifndef` 守卫；
驱动 SDK 侧在 `svcrt_driver_sdk.h` 另加同值守卫。四处的值必须一致。

### 3.2 唤醒原因是**位**，不是值

| 名称 | 值 | 含义 |
|---|---|---|
| `SVCRT_WAKE_NORMAL` | 0 | 正常唤醒（已被派发方认领） |
| `SVCRT_WAKE_TIMEOUT` | 1 | 等待超时 |
| `SVCRT_WAKE_OBJ_DELETED` | 2 | 对象已删除 |
| `SVCRT_WAKE_HANDOFF` | 4 | 派发方明确认领了本任务 |

> `reason == 0` **不是**"拿到令牌"的证明。一次没带 `SVCRT_WAKE_HANDOFF` 的唤醒，
> 有可能是节拍、对象删除等原因顺带产生的。把 `reason == 0` 当成成功判据，
> 就会把失败报成成功。

## 4. 句柄编码

句柄高 12 位是类型标记，低 20 位是对象下标（`SVCRT_HANDLE_MASK = 0xfff00000`）：

| 对象 | 类型标记 | App 侧创建入口 |
|---|---|---|
| 事件 | `SVCRT_EVENT_HANDLE_FLAG` = `0x01100000` | `svcrt_event_create()` |
| 信号量 | `SVCRT_SEM_HANDLE_FLAG` = `0x01300000` | `svcrt_sem_create()` |
| 互斥锁 | `SVCRT_MTX_HANDLE_FLAG` = `0x01400000` | `svcrt_mutex_create()` |
| 消息队列 | `SVCRT_MQ_HANDLE_FLAG` = `0x01500000` | `svcrt_mq_create()` |
| 定时器 | `SVCRT_TIMER_HANDLE_FLAG` = `0x01600000` | `svcrt_timer_create()` |
| 条件变量 | `SVCRT_COND_HANDLE_FLAG` = `0x01700000` | `svcrt_cond_create()` |

每个对象的等待队列容量是 `SVCRT_MAX_SYNC_WAITERS = 4`。第 5 个等待者会拿到 `-2`
（见 §6 规则一），**这不是错误**。

## 5. 各原语语义

### 5.1 信号量 / 互斥锁 / 消息队列 / 定时器

都是"计数/所有权"型对象，等待路径统一：内核登记 → `WOULDBLOCK` → oslib 轮询 → 快路取走。

### 5.2 事件

`svcrt_event_wait(handle, timeout)` 的 flag 快路在内核侧直接返回 0，不进轮询。
oslib 的 `svcrt_event_wait()` 自己记账起止时间，超时那一刻会**再发一次 `timeout=0` 的请求**，
让内核摘除自身登记并回答 `TIMEOUT`（见 §6 规则二）。

### 5.3 条件变量（三步式，不是一步式）

App 侧 `svcrt_cond_wait()` 由三个 SVC 子命令拼成，内核侧**全程不阻塞**：

```
1. cond enqueue (SYNC_CTRL 子命令 14)  把自己挂到条件的等待队列（幂等）
2. mutex unlock  (子命令 7)            放锁；放锁失败就 cond abort 后返回错误
3. 轮询 cond poll (子命令 15)          1 = 被 signal/broadcast 弹出，<0 = 出错
   超时则 cond abort (子命令 16)       摘除自身登记
4. mutex lock (子命令 6, timeout=-1)   不管怎么结束，返回前必须把锁拿回来
```

内核里还留着**子命令 10 = `svcrt_cond_wait_internal()`**（一步式、内核侧阻塞）。
App SDK **不使用它**：它会在 SVC 处理器里阻塞，正好撞上 §1 那条硬约束。
它保留给内核自身调用者，App/驱动一律走 14/15/16。

### 5.4 中断里能做什么

只有两个 `_from_isr` 入口：`svcrt_sem_post_from_isr()` 与 `svcrt_event_set_from_isr()`。
其余同步调用都不保证能在 handler 态安全完成。

## 6. 两条硬规则（踩过才知道）

### 规则一：重复登记返回 `-2` 不是错误

轮询第二次进内核时，任务已经在等待队列里，`waiter_add` 返回 `-2`（已登记）。
**调用点必须能区分 `-2` 与真正的失败。** 曾经 `svcrt_event.c` 与 `svcrt_sync.c` 的
条件变量分支按 `< 0` 判错，把"已经登记"当成失败直接返回，表象是
`evt.wait_timeout` 只过了 1 ms 就回来（上板自检 FAIL）。

> 修法不是"忽略 -2"，而是让每个调用点显式写出
> `if((added < 0) && (added != -2)) { ... }`。写成 `if(added < 0)` 的下一个人还会再踩。

### 规则二：`timeout == 0` 必须摘除自身登记

`timeout=0` 在等待路径上的语义不是"不等待"，而是"把我的登记撤掉并回答 TIMEOUT"。
内核不会给用户态等待者 arm 定时器，所以这条摘除只能由 oslib 在超时那一刻显式发起。
漏了它，等待者会一直挂在队列上，之后每次派发都会去看一个已经走了的任务。

### 附带：服务层幂等 ≠ 内核严格语义

`svcrt_fs_mount()` 拒绝重复挂载（会泄漏旧的 `lfs_t`），这是**内核的严格语义，不能删**。
App 侧"确保已挂载"的诉求在 FILE_SYS 服务层（`svcrt_task.c` 的 case 6）满足：
`(svcrt_fs_mounted() != 0u) ? 0 : svcrt_fs_mount_default()`。
shell 仍保持严格的 mount / unmount 配对。

## 7. 排障入口

### 7.1 `syncinfo` —— 同步对象体检

```
sem  used  count  owner  creator  waiters
 0   1     3      -1     1         t4
  sem 0: posts=12 takes=9 queued=1 last_waiter=t4 qbefore=2 woke=t4 reason=4
sync diagnostics: ghost=0 dup=940
sync ghost  : n=0 idx=-1 tid=t0
sync appwait: hit=480
```

| 字段 | 怎么读 |
|---|---|
| `count` | 令牌当前躺在对象里的数量；`owner` 互斥锁持有者 |
| `waiters` | 挂在队列上的任务，`t<id>` 形式 |
| `posts` / `takes` | 派发 / 取走次数 |
| `qbefore` | 派发那一刻队列里已有几个等待者 |
| `woke` / `reason` | 上一次派发唤醒了谁、原因位是多少（4 = HANDOFF） |
| `ghost` | 没带 `SVCRT_WAKE_HANDOFF` 却被当成成功的唤醒，**必须为 0** |
| `dup` | 重复登记次数。轮询模型下这是正常量（每次轮询都会撞一次 `-2`），不是错误 |
| `appwait hit` | 用户态登记次数，也就是"走了轮询路径"的次数 |

### 7.2 `log` —— 控制台与令牌守恒

```
console   : lock_giveup=0 tx_drop=0 B fifo_full_retries=134831
fifo      : bad_header=0 bytes_lost=0
sync      : ghost=0 dup=940
```

`tx_drop` 才是真实丢失字节数；`fifo_full_retries` 是**被拒尝试数**，不等于丢失。
`bad_header` / `bytes_lost` 非 0 说明 FIFO 缓冲头被写穿（历史上是主栈溢出），
这条路上输出是被静默丢掉的。

### 7.3 `task <id> [任意第三参]` —— 单个任务的现场

```
task 4 sp=0x2001A3B0 st=SUSPENDED frame words:
  sp+0    0x2001A3B8
  ...
  blocks=137 last_reason=4
```

第三个参数只为多打 `blocks=` / `last_reason=` 两行。帧是**原样 56 个字**：
带不带 FPU 扩展帧决定哪个字是 PC，猜哪个字是 PC 就会把回溯变成错答案，
所以这里不给"解析后"的视图。

## 8. 本轮修掉的四个失败（F427 上板自检，均已转绿）

| 自检项 | 表象 | 根因 | 修法 |
|---|---|---|---|
| `evt.wait_timeout` | 1 ms 就返回 | 轮询第二次进内核，`waiter_add` 返回 -2，调用点按 `< 0` 判错 | `svcrt_event.c` / `svcrt_sync.c` 显式容忍 -2 |
| `fs.mount` | App 里挂不上，shell 里能 | `svcrt_fs_mount()` 有意拒绝叠挂（现场回 `littlefs error -1004: a volume is already mounted`） | 内核保留严格语义，FILE_SYS case 6 做幂等 |
| `fs.list_has_new_name` | 新文件名匹配不上 | `names_has` 按 NUL 分隔解析，而 `svcrt_fs_list_names()` 输出是 `\n` 分隔 + 结尾一个 NUL | App 侧改按 `\n` 分隔 |
| `cond.delete` | 返回 0 但报 FAIL | SYNC_CTRL `case 13` 漏 `break`，落到 case 14，返回值被 `svcrt_cond_enqueue_internal()` 覆盖（对象刚删必 -1） | 补 `break` |

> 教训：**switch 漏一个 `break` 会让上层拿到一个"看起来成功了"的返回值。**
> 这类错误的返回值本身不报错，只能靠自检抓。

## 9. 内核同步对象表的容量预算（多 App 并发）

信号量、互斥锁、事件、消息队列、条件变量这五张表是**全局定容**的，容量写在
`kernelsrc/include/svcrt_config.h`（`SVCRT_SEM_NUM` / `SVCRT_MTX_NUM` /
`SVCRT_EVENT_NUM` / `SVCRT_MQ_NUM` / `SVCRT_COND_NUM`）。

关键点：**表满时 `svcrt_sem_create_internal()` 只返回 -1，不区分「名字重复」和「没槽位」**
（`kernelsrc/src/svcrt_sync.c`）。POSIX 层把这个 -1 映射成 `ENOMEM`，
于是表现为 `pthread_create` 失败——**看起来像内存不够，实际是表满**。

### 9.1 每个使用者要占几个槽

| 使用者 | 占用的信号量槽 |
|---|---|
| 每个 POSIX 线程（`pthread_create`） | 2 个（名字形如 `pth<id%10>g` / `pth<id%10>d`） |
| 每个 `sem_t`（`sem_init` / `sem_open`） | 1 个 |
| COND 的等待者 gate | 每个等待中的条件变量等待者另有占用 |

所以**表容量要按「所有并发使用者之和」定，不是按单个 App 峰值定**。

### 9.2 实测案例：开机自检 109/6 → 116/0

同一份 APP_DEMO 镜像曾出现「开机 auto-start 自检 `pass=109 fail=6`（6 项全是 `posix.cond_*`），
运行期 `app stop/start` 却 `pass=116 fail=0`」。

- 先用镜像头逐字段比对（`crc32=0xE59BED1F`、`nominal_base`、`image_size`、`entry_offset`）
  证明板上跑的**与当前源码构建逐字节同源**，排除「旧镜像」这个方向；
- 再按表算账：开机时 POSIX_DEMO 的两个线程活着，占 4 + 1；APP_DEMO 再要 4 + 2 →
  **11 > `SVCRT_SEM_NUM`(8)**，必爆表；
- 运行期重启 APP_DEMO 时，POSIX_DEMO 那边的线程已 join、槽位已归还，所以能过。
- 修法：`SVCRT_SEM_NUM` 8 → 24。F427 重新编译烧录后**开机 auto-start 自检回到 `pass=116 fail=0`**。

> 教训：**表满会伪装成 ENOMEM。** 多 App / 多线程场景下加减线程、加减信号量，
> 都要回头核一遍这几张表的容量。
